# WinDbg Command Coverage

This project follows the Microsoft WinDbg command reference as the command registry baseline.

Reference pages:

- `Commands`: https://learn.microsoft.com/en-us/windows-hardware/drivers/debuggercmds/commands
- `Local Kernel-Mode Debugging`: https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/performing-local-kernel-debugging

## Backend Rule

KnLiveDbg currently has a native live-memory backend, not a KD transport backend. This means commands fall into three groups:

1. Native
   - Can be implemented using the current driver, `DbgHelp`, and local system APIs.
   - Examples: virtual/physical memory display/write/search/compare/fill/move, VA-to-PA translation, module list, symbol lookup, type display, explicit disassembly commands.

2. DbgEng-routed
   - The command exists in the WinDbg command surface, but it needs debugger-engine parser or stop-state semantics.
   - In `auto` or `dbgeng` backend mode, these commands are routed to DbgEng.
   - Examples: execution control, breakpoints, stack walking, registers, source commands, exception commands, I/O port commands.

3. Extension commands
   - Any `!<extension>` command is recognized as an extension command.
   - In `auto` or `dbgeng` backend mode, extension commands are routed to DbgEng.

4. Meta-commands
   - Any unknown `.<command>` is recognized as a WinDbg meta-command.
   - The native backend implements `.sympath`, `.sympath+`, and `.reload`; other meta-commands are routed to DbgEng in `auto` or `dbgeng` mode.

## Backend Commands

```text
backend [auto|native|dbgeng]
kdinit [/local [connect-options]|/remote <connect-options>]
kd <windbg-command>
kddetach
home|dashboard
cls
probe [status|load [sys-path]|info|reset|unload]
ai [status|providers|provider|policy|model|base-url|effort|auth|preview|ask|plan|analyze|explain|annotate|diagnose|playbook|show|run|write|transcript|audit|report]
```

`auto` is the default. Native commands stay on the custom driver backend, while DbgEng-routed commands and extension/meta commands are sent to DbgEng when possible.

Backend mode differences:

| Mode | Native handlers | DbgEng fallback | Typical use |
| --- | --- | --- | --- |
| `auto` | Enabled for implemented live-memory commands. | Enabled for DbgEng-routed commands, `!extension` commands, and unknown `.meta` commands. | Normal mixed operation. |
| `native` | Enabled. | Disabled except for explicit raw escapes such as `kd`. | Verifying driver-backed behavior without accidental raw WinDbg execution. |
| `dbgeng` | Only session/TUI exceptions run before the raw DbgEng catch-all. | Enabled for most commands through `IDebugControl4::ExecuteWide`. | WinDbg parser, stop-state, extension, breakpoint, register, stack, source, trace, and exception commands. |

The `dbgeng` catch-all intentionally excludes `q`, `qq`, `qd`, `quit`, `exit`, `unload`, `drvstatus`, `home`, `dashboard`, `cls`, `probe`, `procctx`, `callbacks`, native `!dml_proc`/`!vad`/`!threads`/`!fwtable`/`!snapshot`/`!diff`/physical bang commands, and `ai` so shutdown, service control, status/dashboard, screen clearing, probe control, native process context, callback/process/firmware-table scanning, session baseline diffing, native physical memory, and AI provider control stay under the TUI. The explicit `u`/`uf` handler also runs before that catch-all. `kd <windbg-command>` always executes a raw DbgEng command regardless of the selected backend mode.

## Implementation Notes

1. `x nt!*Mask*` is handled by splitting `module!symbol-mask` and enumerating the matching loaded kernel module. The `nt` module alias maps to `ntoskrnl.exe`/`ntkrnl*` and is loaded into DbgHelp under the `nt` name.
2. `ln` resolves the input as either a number or symbol, then asks `DbgHelp` for the nearest symbol.
3. `dps`, `dqs`, and `dds` annotate pointer-like values with nearest symbols when available.
4. `dpa`, `dpu`, `dqa`, and `dqu` read a pointer value first, then display the referenced string.
5. Write commands start enabled per handle; `write off` disables the driver gate and `write on` re-enables it.
6. Single transfer size is capped by `KNDBG_MAX_TRANSFER_SIZE`.
7. The build helper copies the pinned `vendor\debugging-tools\x64` Debugging Tools runtime DLLs beside the EXE, with Windows Kits as a fallback; this includes `dbghelp.dll`, `dbgeng.dll`, `dbgcore.dll`, `DbgModel.dll`, `msdia140.dll`, `symsrv.dll`, `srcsrv.dll`, and `symsrv.yes`, and is required for reliable symbol-server downloads and DbgEng runtime loading when the tool is moved to another directory.
8. The sync script, build script, and EXE startup path create `symsrv.yes` when `symsrv.dll` is present but the consent marker is missing.
9. Startup registers staged `msdia140.dll` with `DllRegisterServer` before symbol initialization so DIA fallback works without a separate `regsvr32` step in normal elevated runs. If COM registration is unavailable, DIA fallback can still create `IDiaDataSource` directly from the staged `msdia*.dll` through `DllGetClassObject`.
10. Startup creates `<exe-dir>\symbols` and uses `SRV*<exe-dir>\symbols*https://msdl.microsoft.com/download/symbols` as the default Microsoft symbol server path. It then forces the `nt` kernel image symbols to materialize after the driver is loaded and the ABI is verified, so the kernel PDB is downloaded/loaded into the EXE-local symbol cache before the first type-heavy command. If DbgHelp still reports `SymNone`, the warning includes loaded `dbghelp.dll` and `symsrv.dll` diagnostics.
11. Native `dt` supports layout-only output, value output when an address is supplied, recursive UDT expansion with `-rN`, verbose diagnostics with `-v`, bare output with `-b`, field filters, and wildcard type enumeration such as `dt nt!*EPROCESS*` or `dt nt!*`. Address arguments are resolved by the native address parser and accept simple `+`/`-` arithmetic before type dumping, for example `dt nt!_PS_PROTECTION 0xffffb40c8c1540c0+5fa`. Exact type layouts use `SymGetTypeFromNameW`, then fall back to `SymEnumTypesW` exact matching to recover module base plus type id before DIA is tried; the fallback accepts module-qualified names, leaf type names, and leading-underscore variants. Wildcard patterns use `SymEnumTypesW` with user-mode `*`/`?` filtering and are list-only, with DIA UDT enumeration as fallback when DbgHelp cannot enumerate the type stream. When `DbgHelp` cannot provide a usable UDT layout, DIA fallback recovers field offsets, lengths, bit positions, and type names from the loaded PDB or from a DIA-resolved PDB using the module image plus symbol path. DIA fallback reports whether activation failed, module matching failed, or the specific type was absent from the PDB.
12. `vtop` translates a virtual address to a physical address using the current CR3, a supplied directory-table base, or `/process <process-id>`. The output reports whether the walk used PML4 or PML5, prints the physical address of each page-table entry that was read, and includes the leaf page-table entry physical address plus writable state.
13. `procctx <pid>` stores a process DTB context. `d*` can use `/process <pid>` or the stored context for process-aware user VA physical reads. Native `e*` virtual writes default to the System process context (`pid 4`) and can use `/process <pid>` for one-shot process-aware user VA writes. Address-only `e*` enters a WinDbg-style one-line edit prompt and cancels on an empty line, `.`, `q`, or `quit`. If the leaf PTE/PDE/PDPTE is read-only, `e*` temporarily sets its write bit for the edit, flushes the VA, writes kernel VAs through the original VA, keeps translated user VAs on the physical-write path, restores the write bit afterward, and flushes again. Display reads are sparse, so unreadable bytes stay visible as `??` instead of aborting the whole dump.
14. `phys`, `pdb`, `pdw`, `pdd`, `pdq`, `!db`, `!dw`, `!dd`, and `!dq` read physical memory and use the same sparse `??` display for unreadable ranges; `peb`, `pew`, `ped`, `peq`, `!eb`, `!ew`, `!ed`, and `!eq` write physical memory through the same write gate as virtual writes. Address-only physical enter commands prompt with the current physical value, like the virtual `e*` edit flow. The `!d*` and `!e*` physical-memory commands are intercepted by the TUI before generic DbgEng extension routing.
15. `probe` manages `KnLiveDbgProbe.sys` and prints a deterministic positive-control virtual/physical test buffer plus a test firmware table provider registration (`KNFW`) for `!fwtable` validation.
16. `!dml_proc` is a native process listing command that does not require a DbgEng current process/thread. It resolves PID 4, reads `_EPROCESS.ActiveProcessLinks`, and walks the active process list from live kernel memory. `!dml_proc <pid>` accepts a decimal PID and prints only matching process records.
17. `!vad <pid|image|eprocess> [/summary] [/exec] [/private] [/wx] [/pe] [/hiddenpte] [/limit <n>] [/json <path>]` resolves the target process through the native process walker, resolves VAD fields from PDB/DIA metadata, walks `_EPROCESS.VadRoot` with bounded traversal and cycle protection, and highlights executable private, W+X, large private-executable, and PE-like private regions. `/pe` probes the first page of private VADs through target-DTB translation and the shared PE header probe. `/hiddenpte` walks the target process page tables from the resolved DTB and reports present user PTE ranges that are not covered by any VAD, after suppressing known VAD-less OS shared mappings. JSON output is stable for diffing.
18. `!threads <pid|image|eprocess> [/apc] [/stacks] [/limit <n>] [/json <path>]` walks the target process thread list from PDB-resolved `_EPROCESS.ThreadListHead`/`_ETHREAD.ThreadListEntry`, prints ETHREAD/TID/start/Win32StartAddress/TEB/module/VAD annotations, flags starts outside enumerated user modules or inside suspicious VADs, and optionally reports stack bounds. `/apc` inspects ETHREAD/KAPC APC list fields when symbol metadata exposes them and emits conservative evidence plus warnings on layout drift.
19. `!wfp [providers|sublayers|callouts|filters|layers]` enumerates Windows Filtering Platform objects through the Base Filtering Engine user-mode API in `fwpuclnt.dll`. Providers, sublayers, callouts, filters, and layers each render under a dedicated kind tag with key GUID, decoded flag mnemonics, owning provider name plus service name, applicable layer name, action type, and weight where applicable. `/module <name|GUID>` filters callouts by owning provider; `/layer <name|GUID>` and `/provider <name|GUID>` filter filters by layer or provider. Kernel-mode callout function pointers are intentionally not surfaced because they are not exposed through the user-mode `FWPM_CALLOUT0` shape.
20. `!alpc [ports|port|connections|queues]` enumerates ALPC ports natively from live kernel memory. Port discovery walks the Object Manager namespace from `nt!ObpRootDirectoryObject` with bounded recursion, finds `ALPC Port` and `Directory` types through `nt!ObTypeIndexTable`, decodes `_OBJECT_HEADER.TypeIndex` with the `nt!ObHeaderCookie` XOR formula when available, and follows each port's `_ALPC_PORT.CommunicationInfo` (`ConnectionPort`/`ServerCommunicationPort`/`ClientCommunicationPort`) to surface paired server/client ports that are not themselves named in the directory tree. `connections` groups records by `ConnectionPort` to render server/client family graphs. `queues` counts entries on `MainQueue`, `PendingQueue`, `LargeMessageQueue`, `CanceledQueue`, and `WaitQueue` for a single port; `_KQUEUE` fields are detected by PDB type name and the dispatcher header is skipped before list walking. `/name` and `/pid` filter ports by case-insensitive substring on name/path and by decimal owning-process PID respectively.
19. `!vbs`, `!ci`, and `!securekernel` report Virtualization-Based Security state, Code Integrity options, and Secure Kernel/IUM trustlet presence from live kernel memory. `nt!g_CiOptions` (or `ci!g_CiOptions` / `nt!CiOptions`) is decoded into the 11 documented flag bits. `nt!HvlpVsmVtlCallVa` (with build-specific aliases) is checked for a non-zero kernel-canonical pointer to confirm VBS is active. `PsLoadedModuleList` is scanned for `securekernel.exe` and `skci.dll`. CPUID leaves `0x40000000` and `0x40000006` are queried from user mode for hypervisor vendor identification; MBEC enablement is not claimed because it requires kernel-only MSR reads. `PsActiveProcessHead` is walked with `_EPROCESS`/`_KPROCESS.SecureState` bit 0 (`SecureKernelInProcess`) flagging trustlets; when the field is unavailable, well-known trustlet image-name prefixes (`lsaiso`, `bioiso`, `securesystem`, `kdcustomization`) are used as a fallback.
20. `!etw [loggers|logger <index|name>|integrity]` enumerates ETW logger contexts via `nt!EtwpDebuggerData`'s 64-slot pointer array. The base is resolved through a four-step path (PDB silo, PDB direct, heuristic auto-detect that scores candidate bases by validated `_WMI_LOGGER_CONTEXT` count, legacy `+0x10` as last resort). `WMI_LOGGER_CONTEXT.LoggerName` and `GetCpuClock` are read with PDB priority and documented fallbacks; `GetCpuClock` is interpreted both as a UINT32 mode tag (0/1/2/3 = PerfCounter/SystemTime/CpuCycleCount/Custom) and as a callback pointer. Logger names are sanitised before printing so embedded control characters cannot corrupt console output. `!etw integrity` disassembles the first 16 instructions of canonical kernel dispatch targets across five categories -- ETW pipeline (`EtwpReserveTraceBuffer`, `EtwpReserveTraceBufferAtomic`, `EtwpLogKernelEvent`, `EtwpReleaseTraceBuffer`, `EtwpFinalizeTraceBuffer`, `EtwpCommitTraceBuffer`, `EtwSendTraceBuffer`, `EtwpEventDispatcher`), classic InfinityHook cycle-count (`EtwpGetCycleCount`, `EtwpReceiveCycleCount`), PMC/HAL (`HalpCollectPmcCounters`, `HalCollectPmcCounters`, `HalpProcessorPerfCounter`, `HalpInterruptHandle`), timing sources (`KeQueryPerformanceCounter`, `KeQuerySystemTimePrecise`, `KeQueryInterruptTimePrecise`, `KeQueryUnbiasedInterruptTimePrecise`, `RtlGetSystemTimePrecise`, `HalpTimerQueryHostPerformanceCounter`), and syscall path (`KiSystemCall64`, `KiSystemCall64Shadow`, `KiSystemServiceUser`). Zydis flags first-instruction `jmp`/`int3`/`ud2`, `mov reg,imm64;jmp reg` trampolines, `push imm;ret` trampolines, and any unconditional `call`/`jmp` whose target is kernel-canonical but outside any loaded kernel module. Targets absent from the loaded PDB are reported as `unresolved` and skipped without failing the scan.
21. `!nmi [callbacks]` walks `nt!KiNmiCallbackListHead` (or `nt!KiNmiCallbackList`) through the singly-linked `KNMI_HANDLER_CALLBACK` chain (Next/Callback/Context/Handle at 0x00/0x08/0x10/0x18) with bounded iteration and cycle detection. Each callback is annotated with owning module and nearest symbol; targets outside loaded kernel modules are flagged `[SUSPICIOUS]`.
21ad. `!fwtable [providers|provider <signature>]` and `!fwtable providers /module <name>` passively walk `nt!ExpFirmwareTableProviderListHead` as a `LIST_ENTRY` chain and decode registered firmware table provider nodes. PDB type metadata is preferred when available; otherwise the scanner scores guarded x64 fallback candidates against live nodes before selecting a layout. The normal public-symbol fallback is `SYSTEM_FIRMWARE_TABLE_HANDLER` fields first (`ProviderSignature +0x00`, `Register +0x04`, `FirmwareTableHandler +0x08`, `DriverObject +0x10`) with the list entry at `+0x18`; the older list-entry-first fallback remains available but must win live validation. Output includes signature hex/FourCC, handler module/symbol, DriverObject name/start/size/owner, list links, and notes. Suspicion flags cover non-ACPI/FIRM/RSMB signatures, duplicate signatures, nonkernel or corrupt links, handlers outside loaded kernel images, invalid DriverObjects, unreadable/null/out-of-module DriverStart ownership, and handler/DriverObject owner mismatches. The default scanner never calls `EnumSystemFirmwareTables`, `GetSystemFirmwareTable`, or `ZwQuerySystemInformation(SystemFirmwareTableInformation)` because those paths can invoke registered handlers.
21aa. `!module integrity [module|all] [/summary] [/verbose] [/headers] [/sections] [/wx] [/mismatch] [/limit <n>] [/json <path>]` scans loaded kernel modules from the user-mode module list, reads live PE headers through the driver, validates MZ/PE signatures, optional-header bounds, image/header sizes, alignments, data directories, and section tables, compares the module-list size against `OptionalHeader.SizeOfImage`, and checks executable/`.text` section first/last pages for static W+X section characteristics or effective W+X page permissions through `TranslateVirtual`. The scanner keeps malformed modules as suspicious records without aborting the scan. Console modes cover summary-only, verbose module/section display, header detail, full section detail, W+X-only filtering, and mismatch-only filtering. Stable `kn-live-dbg.module-integrity.v1` JSON includes summary counts, warnings, module reason codes, section reason codes, page-probe state, and notes.
21ab. `!driver integrity [driver|all] [/limit <n>] [/json <path>]` walks `\Driver` through the Object Manager namespace, decodes object type indices with `ObHeaderCookie` when available, reads PDB-resolved `_DRIVER_OBJECT` fields, annotates `MajorFunction[]` pointers with loaded module and nearest symbol, and flags dispatch entries outside loaded modules or routed into another non-kernel module. Common ntoskrnl stubs such as `nt!IopInvalidDeviceRequest` are treated as normal. JSON output uses `kn-live-dbg.driver-integrity.v1`.
21ac. `byovd [scan|update|status]` / `!byovd [scan|update|status]` maintains a local BYOVD catalog under `<exe-dir>\data\byovd` and scans currently loaded kernel modules against it. Options are `/no-update`, `/force-update`, `/exact`, `/yara`, `/yara-path <exe>`, `/yara-timeout <seconds>`, `/verbose`, `/summary`, `/limit <n>`, and `/json <path>`. `tools\update-byovd-intel.ps1` downloads the Microsoft vulnerable driver blocklist ZIP/XML, normalizes hash and file-attribute entries, downloads LOLDrivers hash feeds, and stages LOLDrivers YARA rules. `scan` refreshes the catalog automatically when it is missing or older than 24 hours unless `/no-update` is supplied; `/force-update` refreshes before scanning. The scanner hashes each loaded module image on disk with MD5/SHA1/SHA256, reports exact catalog hits as `HIGH`, optionally runs downloaded LOLDrivers YARA rules through an operator-supplied external `yara64.exe`/`yara.exe` and reports YARA hits as `HIGH`, and reports Microsoft file-name plus PE file-version range hits as `MEDIUM` signer-unverified triage hints after suppressing third-party rule collisions against Microsoft-owned OS binaries with PE version-info vendor metadata. Release packages do not include YARA binaries. `/exact` suppresses name/version hints. JSON output uses `kn-live-dbg.byovd-scan.v1`. `byovd fixture [status|load [sys-path]|unload|path]` controls the bundled no-op `amdryzenmasterdriver.sys` positive-control driver; it should trigger only the Microsoft name/version `MEDIUM` path. If CI policy blocks fixture loading, no loaded-module hit is expected.
21a. `!pool [big|find|summary]` snapshots `nt!PoolBigPageTable` via `NtQuerySystemInformation(SystemBigPoolInformation=0x42)` after enabling `SeDebugPrivilege`. Per-entry filters cover tag (`/tag <ABCD>`, case-sensitive, zero-padded to match `ExAllocatePoolWithTag('SG')` literal encoding), size band (`/min`/`/max`), containing address (`/addr`), paged class (`/nonpaged` default, `/paged`, `/any`), effective W+X (`/wx`), and output cap (`/limit <n>`). With `/annotate`, each kept entry is page-walked through the driver's `IOCTL_KNDBG_TRANSLATE_VIRTUAL` to compute effective R/W/X by ANDing the W bit and ORing the NX bit across every traversed PML5/PML4/PDPTE/PDE/PTE level, and `[W+X]` non-paged allocations are flagged as BYOVD/payload-staging signals. `/wx` implies `/annotate` and applies the output cap after page-attribute filtering so early non-W+X entries do not hide later hits. The `summary` scope suppresses per-entry output and prints only the totals.
21ae. `!snapshot baseline [/all] [/name <label>]`, `!snapshot save <path> [/all] [/name <label>]`, and `!snapshot show [baseline|<path>] [/domains] [/warnings]` implement same-boot evidence baselines over the native scanners. A baseline is kept in session memory and is also written to JSON plus a Markdown report under `.kn-live-dbg\snapshots` and `.kn-live-dbg\reports` unless an explicit JSON path is supplied to `save`. The current domain set is process inventory, modules, drivers/dispatch, callbacks, ETW loggers/integrity, NMI, firmware-table providers, big pool, pool-PE, WFP, ALPC, WNF, VBS/CI, and BYOVD. `!diff baseline` captures a fresh current snapshot, compares against the in-memory baseline with added/escalated-only semantics, scans VAD DKOM hidden-PTE evidence for all newly observed live processes, writes the current JSON and Markdown diff report, and prints domain summaries plus capped findings. Pool findings sort pool-PE suspect, pool-PE hit, W+X NonPaged, then large NonPaged by descending size. Low-risk child records implied by a newly added parent are folded by default and counted as `hiddenChildren`; `/details` expands them. File-to-file diff uses `!diff <old.json> <new.json>` with `/summary`, `/details`, `/domain`, `/risk`, and `/limit`. BYOVD auto-update is disabled for `!diff baseline`; if catalog fingerprints differ between snapshots the diff emits a warning. YARA is not run by the snapshot path.
21b. `dump-raw <address> <length> <path> [/zerofill]` reads `<length>` bytes from `<address>` through the driver `ReadMemory` IOCTL in 256 KB chunks and writes them verbatim to `<path>`. Default behaviour aborts on the first per-chunk failure; `/zerofill` falls back to zero-filling the failed chunk and continuing. Length is capped at 1 GB. `dump-pe <address> <path>` parses the in-memory `IMAGE_DOS_HEADER`/`IMAGE_NT_HEADERS` (PE32 and PE32+) at `<address>`, recomputes the on-disk PE size as `max(SizeOfHeaders, max(PointerToRawData + SizeOfRawData))`, copies the in-memory headers verbatim, and reads each section's `SizeOfRawData` bytes from `<address> + VirtualAddress` to file offset `PointerToRawData`. Failed section reads (typically discarded `INIT`) are zero-filled and surfaced as `[ZERO-FILLED]` warnings so the output remains a structurally-valid PE for IDA/Ghidra. Wiped `MZ` / `PE\0\0` signatures and corrupted `e_lfanew` values are recovered automatically when the surrounding FileHeader/OptionalHeader fields (Machine, NumberOfSections, SizeOfOptionalHeader, OptionalHeader.Magic, SizeOfHeaders/SizeOfImage) are intact enough to identify the NT header position; restored fields are reported with a coloured `recovered=[MZ,e_lfanew,PE]` tag in the summary line.
21c. `pool-scan-pe [/tag <ABCD>] [/min <bytes>] [/max <bytes>] [/limit <n>] [/nonpaged|/paged|/any] [/suspicious] [/dump <directory>]` enumerates big pool entries through the same `SystemBigPoolInformation`-class query as `!pool`, reads each kept entry's first 4 KB, and runs the dump-pe NT header probe (intact or signature-wiped) on the bytes. Hits with any wiped signature (`MZ` / `PE\0\0` / `e_lfanew`) are highlighted as `[pool-pe.suspect]` with a `WIPED=[...]` annotation; hits with all signatures intact print as `[pool-pe.hit]`. `/suspicious` collapses output to wiped hits only. `/dump <directory>` writes each detected PE to `<directory>\poolpe_<tag>_<address>.bin` via the dump-pe section walker so the dropped files are loadable in IDA/Ghidra even with stripped signatures.
21d. `!address <va>` introspects a virtual address: canonicality for LA48 and LA57, zero-page detection, kernel vs user half, the live page-table walk through the driver TranslateVirtual IOCTL (CR3, PML5/PML4/PDPTE/PDE/PTE values with their physical addresses and `(P W U PS NX)` annotations), large-page detection, ANDed effective writable / `!NX` / present / user-accessible across every traversed level, resulting physical address and page offset, owning kernel module + offset, and nearest DbgHelp/DIA symbol with displacement. Symbolic forms (`nt!Foo`, `module+0xN`, expressions) feed through the shared address parser.
21e. `set-ppl-antimalware [on|off|status]` writes the PS_PROTECTION byte (`0x31` = PPL/Antimalware) into the calling process's `_EPROCESS.Protection` field. The field offset is resolved at runtime via `SymbolEngine.FindField("nt!_EPROCESS", "Protection", ...)`, and the driver write goes through `IOCTL_KNDBG_SET_PROCESS_PROTECTION` which requires write mode + the standard write acknowledge magic. `status` reads without mutating; `on` installs PPL Antimalware; `off` clears to 0x00. Required prerequisite for `!ti start`.
21f. `!ti` subscribes to Microsoft-Windows-Threat-Intelligence ETW (provider GUID `f4e1897c-bb5d-5668-f1d8-040f4d8dd344`) via an own session (StartTraceW + EnableTraceEx2 + ProcessTrace), decoding payloads through TDH with a raw-hex fallback and writing one JSON line per event to a rotated log (100 MB x 10). Every event is also pushed into a 1M-event in-memory ring. Default behaviour is silent (ring + log only); `/pid` and `/name` watch targets surface matched events to the TUI through a throttled live queue (default 50/s). `MatchesWatch` checks both caller PID/image and the per-record `TargetProcessId`/`TargetImageBase` fields that `OnEventRecord` pre-extracts from the first non-`CallingProcessId` `*processid` payload field, so cross-process operations (`VirtualAllocEx`, `WriteProcessMemory`, `SetThreadContext`, `QueueUserApc`, ...) are caught from the caller's perspective even when `/name` only names the victim. An empty watch set short-circuits to match-all so `!ti watch` without filters is not silent. Subcommands cover live tail (`!ti watch`, Esc/q/Ctrl+C to exit), ring stats and histograms (`!ti stats`), per-PID/per-task filtering (`!ti by pid` / `!ti by task`), case-insensitive substring grep (`!ti grep`), forensic export (`!ti save`), and runtime watch-set mutation (`!ti add` / `!ti remove`). KnLiveDbg.exe's own events are excluded by default. The handler performs a proactive PPL Antimalware check (reads the EPROCESS.Protection byte for the calling PID through ResolveProcess + ReadMemory, trying multiple `_EPROCESS`/`_KPROCESS` × `DirectoryTableBase`/`Pcb.DirectoryTableBase` field-path combinations to survive PDB drift) and refuses to start when the byte is not `0x31`, with a remediation hint pointing at `set-ppl-antimalware`. Subscription tears down automatically on hard exit (CTRL_CLOSE / CTRL_LOGOFF / CTRL_SHUTDOWN) through a console control handler that calls `Stop()` via a global pointer registered before `Start()`, in addition to the normal dtor path.
22. `!wnf [decode <hash>|instances|instance <hash|entry-address>|data <hash|entry-address>|candidates|lists]` exposes Windows Notification Facility state name decoding and live `_WNF_NAME_INSTANCE` walking through two code paths. `decode` is standalone and always works -- it XORs the 64-bit raw value against `0x41C64E6DA3BC0074` and parses `Version`/`Lifetime` (`WellKnown`/`Permanent`/`Persistent`/`Temporary`) / `DataScope` (`System`/`Session`/`User`/`Process`/`Machine`/`PhysicalMachine`) / `PermanentData` / `Sequence` (53 bits) + `OwnerTag` (4-char ASCII for WellKnown). Live walking first collects silo-state candidates via `nt!ExpWnfSiloState`/`nt!ExpWnfState`/`nt!ExpWnfProcess` and Zydis-driven anchor disassembly of `nt!NtQueryWnfStateData`/`nt!NtPublishWnfStateData` with two levels of indirect-call follow plus dual deref/inline interpretation. The modern Win11 LIST_ENTRY heuristic walker runs first: it enumerates `LIST_ENTRY`-shaped heads in each silo candidate, walks every non-empty chain (bounded), probes byte offsets `0x10`..`0x38` per entry for plausible state-name-shaped 64-bit values (excluding kernel-canonical pointers and zero slots), and ranks each list by the number of UNIQUE state-name values yielded. The single most-diverse list becomes the authoritative `_WNF_NAME_INSTANCE` chain; runner-up lists are surfaced as diagnostics so an operator can spot when the top-1 selection landed on a sentinel chain. When the LIST_ENTRY walker produces no records the legacy `RTL_AVL_TABLE` traversal runs as fallback, locating an AVL-table field on `_WNF_SUBSCRIPTION_TABLE`/`_WNF_SILODRIVERSTATE`/`_WNF_PROCESS_CONTEXT`, performing bounded iterative in-order traversal, and decoding each `_WNF_NAME_INSTANCE` via PDB-resolved `StateName`/`ChangeStamp`/`DataSize`/`LastDataBlock` fields. `instance` and `data` accept either a raw state name or, in LIST_ENTRY mode, the stable entry address printed by `instances`. `data` dumps up to 256 bytes of the last-published payload: the AVL path follows PDB-resolved data-block fields, while the LIST_ENTRY path probes the matched entry for a kernel-canonical pointer whose dereferenced header matches `_WNF_DATA_BLOCK` and emits pointer-census diagnostics when no candidate validates. `candidates` dumps the first 0x100 bytes of every silo candidate with embedded state-name-shape and kernel-pointer counts. `lists` walks every detected LIST_ENTRY head and dumps each chain with per-entry hex/ASCII plus state-name probe annotations. When neither walking mode produces records the scanner reports the precise missing piece and falls back to the standalone decoder.
17. `callbacks [all|object|registry|process|thread|imageload|minifilter] [module]` and `callbacks [scope] /module <module>` parse kernel PDB type layouts and live memory to list object-manager filters, registry callbacks, process/thread/image-load callbacks, and minifilter callbacks with module, symbol, altitude, context, root, and object/filter address annotations. The optional module filter is case-insensitive and is applied after scanning; it keeps records whose pre/function or post callback belongs to the requested module name or module stem. Callback parsing intentionally accepts only canonical scope names, not short aliases.
18. Object callback scanning discovers `_OBJECT_TYPE` objects from `ObTypeIndexTable` before walking each `_OBJECT_TYPE.CallbackList`, with documented type globals used only as fallback. Human output includes the object type name and index when available, so Process, Thread, Desktop, and other object-manager surfaces are explicit instead of requiring the operator to interpret the `_OBJECT_TYPE` address. Public nt PDBs can omit `_CALLBACK_ENTRY_ITEM`; when that happens, the scanner uses a guarded x64 object-callback item layout fallback, validates live list links, callback-entry pointers, operation masks, and callback routine pointers, and treats validated fallback records as normal output. Warnings are reserved for partial PDB layouts, structure drift, or failed live validation.
19. Registry, process, thread, and image-load callback scanning enumerate candidate root symbols and validate the expected list/table shape before emitting records. Public nt PDBs often omit `_CM_CALLBACK_CONTEXT_BLOCK` and `_EX_CALLBACK_ROUTINE_BLOCK`; those scanners use guarded x64 fallback layouts, validate registry callback routines against loaded kernel image ranges, annotate callback routine addresses with module and symbol ownership, print process notify block context values as decoded `notifyType` metadata instead of treating them as module pointers, and preserve image-load notify block/raw slot values for follow-up inspection.
20. Minifilter scanning discovers `fltmgr!FltGlobals`, validates the frame-list root, walks frames and registered filters, and reports operation, unload, instance, name provider, KTM, section, and volume-mount callbacks. Non-exact globals candidates must produce concrete callback records before they are accepted.
21. `u <address|symbol> [instruction-count]` resolves the address natively, including `+`/`-` address arithmetic, reads up to `instruction-count * 16` code bytes through the driver, disassembles them with vendored Zydis, caps explicit counts at 256 instructions, and remembers the next offset for a following bare `u`. If the driver device is not open, the command falls back to the DbgEng disassembly path.
22. `uf <address|symbol> [max-instructions]` resolves the address natively, reads a bounded code window through the driver, disassembles with vendored Zydis, and stops at common function terminal instructions such as `ret`, `iret`, `sysret`, `sysexit`, `hlt`, `ud2`, or `int3`. If the driver device is not open, the command falls back to DbgEng.
23. `kdinit /remote <connection-options>` attaches DbgEng with `DEBUG_ATTACH_KERNEL_CONNECTION`; plain `kdinit` and `kdinit /local` use local-kernel attach.
24. `ai <question>` auto-routes common operator intents before falling back to plain advisory answers: exact read-only command lines such as `callbacks ...`, `dt ...`, `uf ...`, `!ci options`, `!vbs`, or `!fwtable providers` run as evidence and are explained; local capability matches execute through the strict read-only tool catalog, including `fwtable.list` for firmware table provider prompts; unmatched investigative requests automatically create a parsed in-memory `kn-live-dbg.ai-plan.v2` plan. `ai plan <prompt>` remains the explicit planner entrypoint. Plan schema validation rejects empty commands, missing purpose metadata, unsupported backend expectations, command chaining, multiline commands, nested-AI, shutdown/unload, backend/session mutation, probe service control, bare `kd`, raw `kd` blocked-command wrappers, overlong commands, and unknown non-DbgEng commands. `ai run <index|all>` executes only non-write, non-shutdown planned commands through the normal TUI dispatcher.
25. `ai analyze callbacks`, `ai explain <read-only-command...>`, implicit `ai <read-only-command...>`, `ai annotate u|uf`, and `ai diagnose` provide evidence-backed AI assistance on top of implemented native command output. Callback analysis uses normal `callbacks <scope> [module]` evidence. Evidence prompts include deterministic stdout/stderr summaries before raw output.
26. `ai playbook <callbacks|minifilter|object|address|driver>` creates repeatable read-only command plans with dry-run output and optional guarded execution.
27. `ai write <index> confirm` is required to dispatch planned write-like commands and performs backup/read-current plus verification preflight when the write form is recognized. It also renders a deterministic before/after diff for verification stdout/stderr. `ai transcript <path>` captures AI events and command output as JSONL, including output summaries and raw stdout/stderr. `ai transcript max` rotates long transcript files, `ai transcript redact` redacts captured stdout/stderr, `ai audit <path>` captures write-command JSONL audit records, and `ai report <path>` exports the current AI session summary.
28. Interactive command dispatch has a delayed progress watchdog. Silent commands that run longer than about one second emit colored elapsed-time status rows directly to the console with `WriteConsoleW`, outside transcript stdout/stderr capture, and print a final elapsed row only if the watchdog became visible. Once stdout/stderr output starts, progress rows are suppressed for that command to avoid interleaving with long listings such as callback scans.
29. Human-readable console output colorizes high-signal tokens for scanning: callback kind tags, object type names, modules, symbols, translated physical addresses, type/field names, and dump line addresses. The same output remains plain text in stdout capture, AI transcript JSONL, and write-audit JSONL records.
30. The `knkd>` prompt supports Tab completion for registered commands and context-aware subcommands/options, including callback scopes, AI subcommands, backend modes, probe/procctx/write actions, snapshot/diff subcommands and options, `dt` options, `vtop` context options, and `/process` memory command options. Ambiguous prefixes print matching candidates and redraw the current line without dispatching a command. Up/Down recalls recent non-empty commands from the current session history.
31. `tools\build.ps1` stamps `KnLiveDbg.exe`, `KnLiveDbg.sys`, and `KnLiveDbgProbe.sys` with the current PE version without incrementing it by default. `-BumpVersion` increments the patch component, with `0.0.0` as the local baseline and `0.0.1` as the first bumped build. `tools\release.ps1` packages the built PE files, runtime DLLs, symbols/certs when present, and `kn-live-dbg-version.json` into `release\KnLiveDbg-<version>-<configuration>-x64.zip`, using a version-bumped build unless `-NoVersionBump` is supplied.
