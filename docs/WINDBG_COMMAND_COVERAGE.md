# WinDbg Command Coverage

This project follows the Microsoft WinDbg command reference as the command registry baseline.

Reference pages:

- `Commands`: https://learn.microsoft.com/en-us/windows-hardware/drivers/debuggercmds/commands
- `Local Kernel-Mode Debugging`: https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/performing-local-kernel-debugging

## Backend Rule

KnLiveDbg currently has a native live-memory backend, not a KD transport backend. This means commands fall into three groups:

1. Native
   - Can be implemented using the current driver, `DbgHelp`, and local system APIs.
   - Examples: virtual/physical memory display/write/search/compare/fill/move, VA-to-PA translation, module list, symbol lookup, type display, explicit disassembly commands.

2. DbgEng-routed
   - The command exists in the WinDbg command surface, but it needs debugger-engine parser or stop-state semantics.
   - In `auto` or `dbgeng` backend mode, these commands are routed to DbgEng.
   - Examples: execution control, breakpoints, stack walking, registers, source commands, exception commands, I/O port commands.

3. Extension commands
   - Any `!<extension>` command is recognized as an extension command.
   - In `auto` or `dbgeng` backend mode, extension commands are routed to DbgEng.

4. Meta-commands
   - Any unknown `.<command>` is recognized as a WinDbg meta-command.
   - The native backend implements `.sympath`, `.sympath+`, and `.reload`; other meta-commands are routed to DbgEng in `auto` or `dbgeng` mode.


`auto` is the default. Native commands stay on the custom driver backend, while DbgEng-routed commands and extension/meta commands are sent to DbgEng when possible.

Backend mode differences:

| Mode | Native handlers | DbgEng fallback | Typical use |
| --- | --- | --- | --- |
| `auto` | Enabled for implemented live-memory commands. | Enabled for DbgEng-routed commands, `!extension` commands, and unknown `.meta` commands. | Normal mixed operation. |
| `native` | Enabled. | Disabled except for explicit raw escapes such as `kd`. | Verifying driver-backed behavior without accidental raw WinDbg execution. |
| `dbgeng` | Only session/TUI exceptions run before the raw DbgEng catch-all. | Enabled for most commands through `IDebugControl4::ExecuteWide`. | WinDbg parser, stop-state, extension, breakpoint, register, stack, source, trace, and exception commands. |

The `dbgeng` catch-all is **native-first**: any command owned by the TUI/driver path (`IsNativeOwnedCommand`) is never sent to DbgEng. That includes session control (`q`/`unload`/`write`/`probe`/`procctx`/`backend`/`kdinit`/`mcp`/`ai`), native memory (`d*`/`e*`/`phys`/`pe*`/`vtop`/`f`/`m`/`setfield`/`u`/`uf`/`dt`), dumps (`dump-raw`/`dump-pe`), leftover detectors (`!payload`/`!mapper`/`!kpage`/`!pool pe`), PPL (`set-ppl-antimalware`), symbols (`lm`/`x`/`ln`/`.sympath`/`.reload`), and all native bang scanners (`!hunt`/`!ti`/`!timeline`/`!ssdt`/...). Only commands outside that set are raw-executed through DbgEng. `kd <windbg-command>` always executes a raw DbgEng command regardless of the selected backend mode.

## Implementation Notes

1. `x nt!*Mask*` is handled by splitting `module!symbol-mask` and enumerating the matching loaded kernel module. The `nt` module alias maps to `ntoskrnl.exe`/`ntkrnl*` and is loaded into DbgHelp under the `nt` name.
2. `ln` resolves the input as either a number or symbol, then asks `DbgHelp` for the nearest symbol.
3. `dps`, `dqs`, and `dds` annotate pointer-like values with nearest symbols when available.
4. `dpa`, `dpu`, `dqa`, and `dqu` read a pointer value first, then display the referenced string.
5. Write commands start enabled per handle; `write off` disables the driver gate and `write on` re-enables it.
6. Single transfer size is capped by `KNDBG_MAX_TRANSFER_SIZE`.
7. The build helper copies the pinned `vendor\debugging-tools\x64` Debugging Tools runtime DLLs beside the EXE, with Windows Kits as a fallback; this includes `dbghelp.dll`, `dbgeng.dll`, `dbgcore.dll`, `DbgModel.dll`, `msdia140.dll`, `symsrv.dll`, `srcsrv.dll`, and `symsrv.yes`, and is required for reliable symbol-server downloads and DbgEng runtime loading when the tool is moved to another directory.
8. The sync script, build script, and EXE startup path create `symsrv.yes` when `symsrv.dll` is present but the consent marker is missing.
9. Startup registers staged `msdia140.dll` with `DllRegisterServer` before symbol initialization so DIA fallback works without a separate `regsvr32` step in normal elevated runs. If COM registration is unavailable, DIA fallback can still create `IDiaDataSource` directly from the staged `msdia*.dll` through `DllGetClassObject`.
10. Startup creates `<exe-dir>\symbols` and uses `SRV*<exe-dir>\symbols*https://msdl.microsoft.com/download/symbols` as the default Microsoft symbol server path. It then forces the `nt` kernel image symbols to materialize after the driver is loaded and the ABI is verified, so the kernel PDB is downloaded/loaded into the EXE-local symbol cache before the first type-heavy command. If DbgHelp still reports `SymNone`, the warning includes loaded `dbghelp.dll` and `symsrv.dll` diagnostics.
11. Native `dt` supports layout-only output, value output when an address is supplied, recursive UDT expansion with `-rN`, verbose diagnostics with `-v`, bare output with `-b`, field filters, and wildcard type enumeration such as `dt nt!*EPROCESS*` or `dt nt!*`. Address arguments are resolved by the native address parser and accept simple `+`/`-` arithmetic before type dumping, for example `dt nt!_PS_PROTECTION 0xffffb40c8c1540c0+5fa`. Exact type layouts use `SymGetTypeFromNameW`, then fall back to `SymEnumTypesW` exact matching to recover module base plus type id before DIA is tried; the fallback accepts module-qualified names, leaf type names, and leading-underscore variants. Wildcard patterns use `SymEnumTypesW` with user-mode `*`/`?` filtering and are list-only, with DIA UDT enumeration as fallback when DbgHelp cannot enumerate the type stream. When `DbgHelp` cannot provide a usable UDT layout, DIA fallback recovers field offsets, lengths, bit positions, and type names from the loaded PDB or from a DIA-resolved PDB using the module image plus symbol path. DIA fallback reports whether activation failed, module matching failed, or the specific type was absent from the PDB.
12. `vtop` translates a virtual address to a physical address using the current CR3, a supplied directory-table base, or `/process <process-id>`. The output reports whether the walk used PML4 or PML5, prints the physical address of each page-table entry that was read, and includes the leaf page-table entry physical address plus writable state.
13. `procctx <pid>` stores a process DTB context. `d*` can use `/process <pid>` or the stored context for process-aware user VA physical reads. Native `e*` virtual writes default to the System process context (`pid 4`) and can use `/process <pid>` for one-shot process-aware user VA writes. Address-only `e*` enters a WinDbg-style one-line edit prompt and cancels on an empty line, `.`, `q`, or `quit`. If the leaf PTE/PDE/PDPTE is read-only, `e*` temporarily sets its write bit for the edit, flushes the VA, writes kernel VAs through the original VA, keeps translated user VAs on the physical-write path, restores the write bit afterward, and flushes again. Display reads are sparse, so unreadable bytes stay visible as `??` instead of aborting the whole dump.
14. `phys`, `pdb`, `pdw`, `pdd`, `pdq`, `!db`, `!dw`, `!dd`, and `!dq` read physical memory and use the same sparse `??` display for unreadable ranges; `peb`, `pew`, `ped`, `peq`, `!eb`, `!ew`, `!ed`, and `!eq` write physical memory through the same write gate as virtual writes. Address-only physical enter commands prompt with the current physical value, like the virtual `e*` edit flow. The `!d*` and `!e*` physical-memory commands are intercepted by the TUI before generic DbgEng extension routing.
15. `probe` manages `KnLiveDbgProbe.sys` and prints a deterministic positive-control virtual/physical test buffer plus a test firmware table provider registration (`KNFW`) for `!fwtable` validation.
16. `!dml_proc` is a native process listing command that does not require a DbgEng current process/thread. It resolves PID 4, reads `_EPROCESS.ActiveProcessLinks`, and walks the active process list from live kernel memory. `!dml_proc <pid|name>` accepts either a decimal PID or a case-insensitive image-name substring and prints only matching process records.
17. `!vad <pid|image|eprocess> [/summary] [/exec] [/private] [/wx] [/pe] [/hiddenpte] [/limit <n>] [/json <path>]` resolves the target process through the native process walker, resolves VAD fields from PDB/DIA metadata, and walks `_EPROCESS.VadRoot` with bounded traversal and cycle protection. Child links are queued before optional record metadata is decoded; when only one child pointer is readable that known subtree is still visited. Filters and `/limit` apply to output only, while total and matching counts reflect the full traversal. Kernel VAD protection is preserved as allocation/default metadata; a complete `VirtualQueryEx` walk records current committed executable, writable, copy-on-write, W+X, execute-copy-on-write, and `MEM_IMAGE` evidence plus address ranges. `/wx` uses those current ranges when available. `/pe` probes committed private VAD base pages through target-DTB translation and the shared PE header probe. `/hiddenpte` walks the target process page tables from its resolved DTB and reports present user PTE ranges that are not covered by a VAD, after suppressing known VAD-less OS shared mappings. `!vad scan <pid|eprocess>` combines private executable, W+X, intact/wiped private PE, large private executable, and hidden-PTE evidence; an empty user-process VAD root or incomplete exact-process protection view fails coverage closed. `!vad modules <pid|eprocess>` merges Toolhelp loader modules, all VAD allocation bases, `VirtualQueryEx` `MEM_IMAGE` identity, in-memory PE header/entry-point probes, and `K32GetMappedFileNameW` paths to report every observable loaded or mapped PE, including loader-invisible private/manual and SEC_IMAGE mappings with decommitted headers or nonstandard extensions. JSON schemas are `kn-live-dbg.vad.v1` and `kn-live-dbg.process-pe.v1`, with independent traversal, effective-protection, PE-probe, loader, header, mapped-path, and aggregate coverage fields. `tools/validate-process-vad.ps1` exercises every filter and both modes against multi-region positive controls by PID and EPROCESS.
18. `!threads <pid|image|eprocess> [/apc] [/stacks] [/limit <n>] [/json <path>]` walks the target process thread list from PDB-resolved `_EPROCESS.ThreadListHead`/`_ETHREAD.ThreadListEntry`, prints ETHREAD/TID/start/Win32StartAddress/TEB/module/VAD annotations, and optionally reports stack bounds. Thread, stack, and APC correlation checks the current protection of the exact referenced address instead of inheriting aggregate permissions from the whole VAD; loader-view absence alone remains telemetry unless private/W+X page provenance, PE/large-region evidence, an identity violation, or a noncanonical address corroborates it. `/apc` inspects ETHREAD/KAPC APC list fields when symbol metadata exposes them and, for current `ntdll.dll` user-APC dispatchers, safely resolves a suspicious executable callback carried in the context/argument slots while leaving ordinary data arguments as telemetry.
19. `!wfp [providers|sublayers|callouts|filters|layers]` enumerates Windows Filtering Platform objects through the Base Filtering Engine user-mode API in `fwpuclnt.dll`. Providers, sublayers, callouts, filters, and layers each render under a dedicated kind tag with key GUID, decoded flag mnemonics, owning provider name plus service name, applicable layer name, action type, and weight where applicable. `/module <name|GUID>` filters callouts by owning provider; `/layer <name|GUID>` and `/provider <name|GUID>` filter filters by layer or provider. `!wfp kernelcallouts` additionally recovers the kernel-mode classify/notify/flowDelete function pointers that `FWPM_CALLOUT0` does not expose: it anchors on `netio!gWfpGlobal`, scores documented callout-table layouts against live classify pointers (bounded offset-scan fallback for drift), walks the callout array, joins each slot to the user-mode callout metadata by callout id, and flags `[SUSPICIOUS]` any classify target outside every loaded kernel module. It requires the driver device plus netio.sys symbols, reuses the memory-read primitive (no new IOCTL), and reports cleanly when the layout cannot be located. Intercepted by the TUI before the DbgEng catch-all.
20. `!alpc [ports|port|connections|queues]` enumerates ALPC ports natively from live kernel memory. Port discovery walks the Object Manager namespace from `nt!ObpRootDirectoryObject` with bounded recursion, finds `ALPC Port` and `Directory` types through `nt!ObTypeIndexTable`, decodes `_OBJECT_HEADER.TypeIndex` with the `nt!ObHeaderCookie` XOR formula when available, and follows each port's `_ALPC_PORT.CommunicationInfo` (`ConnectionPort`/`ServerCommunicationPort`/`ClientCommunicationPort`) to surface paired server/client ports that are not themselves named in the directory tree. `connections` groups records by `ConnectionPort` to render server/client family graphs. `queues` counts entries on `MainQueue`, `PendingQueue`, `LargeMessageQueue`, `CanceledQueue`, and `WaitQueue` for a single port; `_KQUEUE` fields are detected by PDB type name and the dispatcher header is skipped before list walking. `/name` and `/pid` filter ports by case-insensitive substring on name/path and by decimal owning-process PID respectively.
19. `!vbs`, `!ci`, and `!securekernel` report Virtualization-Based Security state, Code Integrity options, and Secure Kernel/IUM trustlet presence from live kernel memory. `nt!g_CiOptions` (or `ci!g_CiOptions` / `nt!CiOptions`) is decoded into the 11 documented flag bits. `nt!HvlpVsmVtlCallVa` (with build-specific aliases) is checked for a non-zero kernel-canonical pointer to confirm VBS is active. `PsLoadedModuleList` is scanned for `securekernel.exe` and `skci.dll`. CPUID leaves `0x40000000` and `0x40000006` are queried from user mode for hypervisor vendor identification; MBEC enablement is not claimed because it requires kernel-only MSR reads. `PsActiveProcessHead` is walked with `_EPROCESS`/`_KPROCESS.SecureState` bit 0 (`SecureKernelInProcess`) flagging trustlets; when the field is unavailable, well-known trustlet image-name prefixes (`lsaiso`, `bioiso`, `securesystem`, `kdcustomization`) are used as a fallback.
20. `!etw [loggers|logger <index|name>|integrity|providers|ti-cross]` enumerates ETW logger contexts via `nt!EtwpDebuggerData`'s 64-slot pointer array. The base is resolved through a four-step path (PDB silo, PDB direct, heuristic auto-detect that scores candidate bases by validated `_WMI_LOGGER_CONTEXT` count, legacy `+0x10` as last resort). `WMI_LOGGER_CONTEXT.LoggerName` and `GetCpuClock` are read with PDB priority and documented fallbacks; `GetCpuClock` is interpreted both as a UINT32 mode tag (0/1/2/3 = PerfCounter/SystemTime/CpuCycleCount/Custom) and as a callback pointer. Logger names are sanitised before printing so embedded control characters cannot corrupt console output. `!etw integrity` disassembles the first 16 instructions of canonical kernel dispatch targets across five categories -- ETW pipeline (`EtwpReserveTraceBuffer`, `EtwpReserveTraceBufferAtomic`, `EtwpLogKernelEvent`, `EtwpReleaseTraceBuffer`, `EtwpFinalizeTraceBuffer`, `EtwpCommitTraceBuffer`, `EtwSendTraceBuffer`, `EtwpEventDispatcher`), classic InfinityHook cycle-count (`EtwpGetCycleCount`, `EtwpReceiveCycleCount`), PMC/HAL (`HalpCollectPmcCounters`, `HalCollectPmcCounters`, `HalpProcessorPerfCounter`, `HalpInterruptHandle`), timing sources (`KeQueryPerformanceCounter`, `KeQuerySystemTimePrecise`, `KeQueryInterruptTimePrecise`, `KeQueryUnbiasedInterruptTimePrecise`, `RtlGetSystemTimePrecise`, `HalpTimerQueryHostPerformanceCounter`), and syscall path (`KiSystemCall64`, `KiSystemCall64Shadow`, `KiSystemServiceUser`). Zydis flags first-instruction `jmp`/`int3`/`ud2`, `mov reg,imm64;jmp reg` trampolines, `push imm;ret` trampolines, and any unconditional `call`/`jmp` whose target is kernel-canonical but outside any loaded kernel module. Targets absent from the loaded PDB are reported as `unresolved` and skipped without failing the scan.
21. `!nmi [callbacks]` walks `nt!KiNmiCallbackListHead` (or `nt!KiNmiCallbackList`) through the singly-linked `KNMI_HANDLER_CALLBACK` chain (Next/Callback/Context/Handle at 0x00/0x08/0x10/0x18) with bounded iteration and cycle detection. Each callback is annotated with owning module and nearest symbol; targets outside loaded kernel modules are flagged `[SUSPICIOUS]`.
21ag. `!msrcheck` reads the SYSCALL-configuration MSRs (`IA32_LSTAR`/`CSTAR`/`STAR`/`FMASK`/`EFER`) on every active processor in group 0 through the read-only `IOCTL_KNDBG_READ_MSR` primitive (ABI version 8; the driver permits only a fixed architectural MSR whitelist and pins per-CPU affinity). `LSTAR` that does not equal `nt!KiSystemCall64`, any per-CPU divergence, and entry pointers outside the loaded kernel image are flagged `[SUSPICIOUS]` as possible SYSCALL hooks; `CSTAR` is validated only when non-zero; `STAR` selectors and `EFER` bits are decoded for inspection. It is intercepted by the TUI before the DbgEng catch-all and is the first slice of the CPU-state detection family.
21ah. `!cr` reads CR0/CR4/CR8 on every active processor in group 0 through the read-only `IOCTL_KNDBG_READ_CONTROL_REGISTERS` primitive (ABI version 9; same per-CPU affinity-pinned pattern as `!msrcheck`). `CR0.WP=0` and any per-CPU divergence of CR0/CR4 are flagged `[SUSPICIOUS]`; CR4 mitigation bits (SMEP/SMAP/UMIP/LA57/CET/PKE) are decoded and SMEP/SMAP-off is surfaced as a mitigation-weakened note. Intercepted by the TUI before the DbgEng catch-all.
21ai. `!ssdt` walks the native SSDT (`nt!KeServiceDescriptorTable` -> `KiServiceTable`) and, when win32k modules are loaded, the win32k shadow table (`nt!KeServiceDescriptorTableShadow[1]`). It needs no new driver IOCTL -- it reuses the memory-read primitive and the PDB-first layout resolver for `_KSERVICE_TABLE_DESCRIPTOR` Base/Limit. Each routine is decoded as `KiServiceTable + (entry >> 4)` and flagged `[SUSPICIOUS]` when it falls outside the expected image (ntoskrnl for native, `win32k*` for shadow) or outside all loaded modules. Only hooked entries are listed; clean tables print a one-line summary. Intercepted by the TUI before the DbgEng catch-all.
21aj. `!idt` reads the boot processor IDTR through the read-only `IOCTL_KNDBG_READ_IDT` primitive (ABI version 10; `__sidt` under the per-CPU affinity-pinned pattern), walks the interrupt gate descriptors, rebuilds each handler (`OffsetLow | Middle<<16 | High<<32`), and flags `[SUSPICIOUS]` any present gate whose handler is outside every loaded kernel module. It also cross-checks every active processor's IDT against the boot processor and flags `[SUSPICIOUS]` any vector whose handler diverges across cores (a single-core interrupt-hook signal). Only flagged gates are listed; a clean table prints a one-line summary with `cpus-compared=N`. The modern Win11 LIST_ENTRY heuristic walker runs first: it enumerates `LIST_ENTRY`-shaped heads in each silo candidate, walks every non-empty chain (bounded), probes byte offsets `0x10`..`0x38` per entry for plausible state-name-shaped 64-bit values (excluding kernel-canonical pointers and zero slots), and ranks each list by the number of UNIQUE state-name values yielded. The single most-diverse list becomes the authoritative `_WNF_NAME_INSTANCE` chain; runner-up lists are surfaced as diagnostics so an operator can spot when the top-1 selection landed on a sentinel chain. When the LIST_ENTRY walker produces no records the legacy `RTL_AVL_TABLE` traversal runs as fallback, locating an AVL-table field on `_WNF_SUBSCRIPTION_TABLE`/`_WNF_SILODRIVERSTATE`/`_WNF_PROCESS_CONTEXT`, performing bounded iterative in-order traversal, and decoding each `_WNF_NAME_INSTANCE` via PDB-resolved `StateName`/`ChangeStamp`/`DataSize`/`LastDataBlock` fields. `instance` and `data` accept either a raw state name or, in LIST_ENTRY mode, the stable entry address printed by `instances`. `data` dumps up to 256 bytes of the last-published payload: the AVL path follows PDB-resolved data-block fields, while the LIST_ENTRY path probes the matched entry for a kernel-canonical pointer whose dereferenced header matches `_WNF_DATA_BLOCK` and emits pointer-census diagnostics when no candidate validates. `candidates` dumps the first 0x100 bytes of every silo candidate with embedded state-name-shape and kernel-pointer counts. `lists` walks every detected LIST_ENTRY head and dumps each chain with per-entry hex/ASCII plus state-name probe annotations. When neither walking mode produces records the scanner reports the precise missing piece and falls back to the standalone decoder.
17. `!callbacks [all|object|registry|process|thread|imageload|minifilter] [module]` and `!callbacks [scope] /module <module>` parse kernel PDB type layouts and live memory to list object-manager filters, registry callbacks, process/thread/image-load callbacks, and minifilter callbacks with module, symbol, altitude, context, root, and object/filter address annotations. The optional module filter is case-insensitive and is applied after scanning; it keeps records whose pre/function or post callback belongs to the requested module name or module stem, plus same-session disabled slots for that module. `!callbacks disable <scope> <module>` / `enable` and `disable-all` / `enable-all` patch only that module: Ob/Cm/Ps function pointers become a CFG-valid return-0 thunk; minifilter reuses `!minifilter` SetAllIrps (Pre=1, Post=0, live CallbackNodes). Writes never use NULL or list unlink, require `write on`, and restore only same-session backups. Disabled rows print `DISABLED`. JSON schema `kn-live-dbg.callbacks-set.v1`. MCP write tool is `callbacks.set`. Callback parsing intentionally accepts only canonical scope names, not short aliases.
18. Object callback scanning discovers `_OBJECT_TYPE` objects from `ObTypeIndexTable` before walking each `_OBJECT_TYPE.CallbackList`, with documented type globals used only as fallback. Human output includes the object type name and index when available, so Process, Thread, Desktop, and other object-manager surfaces are explicit instead of requiring the operator to interpret the `_OBJECT_TYPE` address. Public nt PDBs can omit `_CALLBACK_ENTRY_ITEM`; when that happens, the scanner uses a guarded x64 object-callback item layout fallback, validates live list links, callback-entry pointers, operation masks, and callback routine pointers, and treats validated fallback records as normal output. Warnings are reserved for partial PDB layouts, structure drift, or failed live validation.
19. Registry, process, thread, and image-load callback scanning enumerate candidate root symbols and validate the expected list/table shape before emitting records. Public nt PDBs often omit `_CM_CALLBACK_CONTEXT_BLOCK` and `_EX_CALLBACK_ROUTINE_BLOCK`; those scanners use guarded x64 fallback layouts, validate registry callback routines against loaded kernel image ranges, annotate callback routine addresses with module and symbol ownership, print process notify block context values as decoded `notifyType` metadata instead of treating them as module pointers, and preserve image-load notify block/raw slot values for follow-up inspection.
20. Minifilter scanning discovers `fltmgr!FltGlobals`, validates the frame-list root, walks frames and registered filters, and reports operation, unload, instance, name provider, KTM, section, and volume-mount callbacks. Non-exact globals candidates must produce concrete callback records before they are accepted.
21. `u <address|symbol> [instruction-count]` resolves the address natively, including `+`/`-` address arithmetic, reads up to `instruction-count * 16` code bytes through the driver, disassembles them with vendored Zydis, caps explicit counts at 256 instructions, and remembers the next offset for a following bare `u`. If the driver device is not open, the command falls back to the DbgEng disassembly path.
22. `uf <address|symbol> [max-instructions]` resolves the address natively, reads a bounded code window through the driver, disassembles with vendored Zydis, and stops at common function terminal instructions such as `ret`, `iret`, `sysret`, `sysexit`, `hlt`, `ud2`, or `int3`. If the driver device is not open, the command falls back to DbgEng.
21al. `!threads` and `!hunt` resolve `_ETHREAD.SuspendCount` and `FreezeCount` recursively through PDB/DIA metadata. Thread JSON preserves both raw counts, per-field availability, stable thread-list inventory state, and independent suspend-state coverage. Hunt emits high-risk/high-confidence `security_tool_impairment` only when the inventory and state reads are complete, every observed thread of a known security-product process has a nonzero suspend or freeze count, and the same per-ETHREAD counts are reproduced by a second fresh scan. Mixed runnable/suspended state, a transient or changing all-suspended sample, unknown process identity, unresolved fields, capped records, and unstable list traversal are negative controls; unstable evidence marks coverage incomplete rather than clean.
21am. Snapshot capture adds a `process-security` record for each readable `_EPROCESS.Protection` byte and preserves callback/module coverage metadata. Imported JSON must keep the process-security tags, derived Protection fields, read counts, coverage flag, and process-record ownership internally consistent. Same-boot `!diff` promotes a stable process identity whose Protection byte changes; downgrade or strip is high risk, while an upward/other change is medium. It also reports removal of a protection record when current process-security coverage is complete and the owning process remains present. General removals remain hidden, but a callback removal is reported when current callback and module coverage are complete, the callback owner module remains loaded, and no semantically equivalent callback was re-registered at a different list address. Cross-boot, incomplete-coverage, owner-unload, and semantic re-registration cases are suppressed. Diff console/Markdown/domain summaries include an explicit `removed` counter.
21an. Default/deep `!hunt` enumerates `MSFT_NetQosPolicySettingData` directly from `ROOT\StandardCimv2`, so volatile `ActiveStore` policy is inspected independently of WFP Block filters. A policy is promoted only when `AppPathNameMatchCondition` resolves to a known security-product executable and `ThrottleRateAction` is present, nonzero, and at most 64 KiB/s; at most 1 KiB/s is high risk. Findings preserve policy identity/store, owner, target, byte/bit rates, profile, and precedence. The summary includes total/suspicious QoS counts plus `qos_policy_coverage_incomplete`; WMI failure or a partial enumeration marks aggregate hunt coverage incomplete rather than reporting a clean result. `tools\run-qos-bind-e2e.ps1` creates a unique 64-bit/s nonpersistent `ActiveStore` policy for only its temporary `MsSense.exe` fixture path and independently requires the exact policy, target, 8-byte/s WMI value, 64-bit/s derived value, and complete coverage.
21ao. Default/deep `!hunt` dynamically resolves the system `bindfltapi!BfGetMappings` interface and enumerates global mappings for every mounted local fixed/removable/RAM volume, including mounted-folder-only volumes discovered through `FindFirstVolume` plus `GetVolumePathNamesForVolumeName`; a partial volume walk leaves global coverage incomplete. The parser requires `S_OK`, returned `STATUS_SUCCESS`, and a nonzero returned size, and bounds-checks the header, mapping/target arrays, structural-region non-overlap, UTF-16 alignment/offsets/lengths, count multiplication, and a 16 MiB growth cap. Root-relative paths are anchored to the enumerated volume before trust-boundary, inverse-pair, and process-backing correlation, while protected-directory recognition uses authoritative Windows and known-folder roots. An exact mapping is promoted only when it intersects a known security-product path, `amsi.dll` or an event-log artifact, crosses a protected/user-controlled path boundary in either direction, redirects a Windows system image to a different image, or forms a same-volume inverse mapping pair. A separate per-process rule requires an exact visible source-path match plus resolved, agreeing EPROCESS main-section and main-image VAD backing paths equal to one active target; this emits `bind_link_process_binding_state` and `bind_link_process_backing_correlation`. If a candidate source process exists but either backing view is unresolved, JSON sets `bindflt_process_correlation_coverage_incomplete=true` and aggregate coverage incomplete without emitting the Process-Binding finding. `KnLiveDbgBindFixture.exe` is deliberately not a general bind utility: it can apply/remove only two fixed source/target pairs under one direct GUID-named Windows temporary directory and rejects other roots, nesting, reparse points, missing apply files, and same-file endpoints. Removal remains available for the exact constrained path after fixture-file loss and accepts only `S_OK` or an already-missing mapping. The elevated runner verifies redirected text and executable hashes, launches only the copied benign backing process, captures one hunt, and applies `tools\validate-qos-bind-e2e.ps1` to exact global mapping, live-PID, visible-source, two-backing-view, counters, and warning state before verified cleanup. Its driver-free validator corpus covers the positive contract and malformed, incomplete, mistyped, missing, and contradictory controls. JSON preserves mapping, suspicious, Process-Binding, and global coverage counts/states separately from `bindflt_silo_coverage_unsupported=true`: enumerating silo-scoped mappings still requires discovering and querying each specific silo Job handle, so global coverage is not represented as full File/Process/Silo-Binding coverage.
21ap. Default/deep `!hunt` inspects each resolved SEC_IMAGE VAD backing path for current-state CloudFiles False File Immutability provenance. `CloudFileScanner` opens the primary handle with `FILE_READ_ATTRIBUTES`, keeps `cldflt` in the path, and performs a separate bounded `FSCTL_GET_REPARSE_POINT` metadata cross-view without reading file data. It recognizes `IO_REPARSE_TAG_CLOUD` plus all masked variants when either tag view exposes them. On current builds where `cldflt` masks the tag from both views, successful dynamic `cldapi!CfGetPlaceholderInfo` metadata is an authoritative identity fallback; evidence records the fallback and FSCTL error rather than misclassifying the image as a normal file. The scanner also resolves `CfGetPlaceholderStateFromFileInfo` when a tag is visible and bounds-checks the variable-length `CF_PLACEHOLDER_STANDARD_INFO` identity payload with a 64 KiB cap. It preserves tag/state, on-disk/validated/modified/property sizes, pin and sync state, file and sync-root ids, and identity length. The hunt reads `_EPROCESS.Protection` from the active symbol layout and emits `cloudfiles_false_file_immutability` only for a PP/PPL placeholder-backed image, positive `ModifiedDataSize`, or correlation with an existing normalized deep executable live-versus-disk mismatch. The in-sync, unmodified, non-PP/PPL mapping is a negative control. JSON exposes placeholder/suspicious counts and separate metadata/protection-correlation incomplete flags; missing metadata is not promoted. Its additive `cloudfiles_images` array retains every metadata-complete positive and negative observation with exact PID, module/VAD identity, raw state, protection correlation, decision, and reasons; clean-host and E2E validators require exact summary/array agreement. `tools\run-cloudfiles-placeholder-fixture.ps1` provides safe `InSyncNegative` and `ModifiedPositive` live contracts using an `ALWAYS_FULL`, never-dehydrated copied system image. From an elevated PowerShell session, `-ValidateHunt` keeps the exact fixture PID alive for one Deep hunt and applies `tools\validate-cloudfiles-hunt-e2e.ps1` to the resulting artifact. This is a current-state invariant and does not claim historical dehydrate/rehydrate callback or file-generation reconstruction.
21aq. `!snapshot` captures the documented Filter Manager attachment view through bounded `FilterVolumeFindFirst/Next` and `FilterVolumeInstanceFindFirst/Next(InstanceAggregateStandardInformation)` calls. Snapshot records retain every enumerated volume plus minifilter/legacy attachment identity, altitude, frame, filesystem type, supported features, aggregate flags, instance flags, and `FLTFL_IASIM_DETACHED_VOLUME`; parser failure, access denial, duplicate identities, malformed offsets/lengths, or a partial per-volume query leaves `minifilter_attachments_coverage_complete=false`. Static detached state remains low-risk telemetry because teardown can be legitimate. Same-boot `!diff` promotes only an attached-to-detached transition, or a missing minifilter attachment when current attachment/callback coverage is complete, the same volume persists, and the independently walked registered-minifilter callback view still contains the filter. A clean same-filter/same-volume attachment suppresses removal only when the baseline altitude remains present, or when altitude is unavailable and the instance name remains present; a different-altitude decoy cannot suppress removal. Filter unload, volume removal, incomplete coverage, and cross-boot comparison suppress the removal finding.
