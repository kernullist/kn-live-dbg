# 동시 감시 이미지 순회 검증 (2026-10-24)

기준은 `57c8314`다. [실제 vctip 검증](KMON_VCTIP_VALIDATION_20261024.md)에서 남긴
13개 대조군 동시 감시 조건의 System.Data partial과 배경 검사 범위를 다시 조사했다.
원본 실행·캡처·독립 계산은 `.build/kmon-vctip-load-20261024`에 보존한다.

## 원인과 변경

기존 스케줄러는 프로세스를 먼저 순환한 뒤 그 프로세스 안에서 최초 순회를
우선했다. 따라서 최초 순회가 남은 DLL이 많은 vctip도 재검사만 필요한 다른
프로세스마다 한 차례씩 기다렸다. 최초 검사 우선순위가 프로세스 사이에는 적용되지
않았다. 완료 이미지가 캐시에서 제거되면 30초 대기 후 순회 이력도 없어져 새 작업처럼
경쟁했다. 최초·재검사 배분에 쓰는 이미지별 차례 합계도 제거 시 초기화됐다.

- 감시·배경 그룹의 기존 3:1 배분을 유지하고, 각 그룹에서 최초 순회·재검사도
  3:1로 선택한다. 종류를 먼저 선택한 뒤 프로세스 세대와 이미지의 차례를 순환한다.
  배분 카운터는 이미지 작업이 제거되어도 유지된다. 비어 있는 종류의 차례는 재사용한다.
- 감시 최초 순회 몫이 비면 배경의 최초 순회에 빌려 준다. 감시 재검사 차례와
  배경의 기본 몫은 유지한다. 빌려준 차례에서도 원래 배분 카운터를 전진시켜
  감시 재검사 차례가 사라지지 않게 한다. 준비된 그룹이 하나뿐이면 전체를 배정한다.
- 배경 최초 순회 차례의 2/3는 대형 이미지에 배정한다. 실제 차례와 빌린 차례를
  pipeline 지표로 기록한다.
- 순회를 마친 작업을 제거한 뒤 식별자 기록을 보관한다. 30초 대기가 끝나면 파일 식별자를
  다시 확인하여 재검사로 분류한다. 일치하는 식별자를 확인한 뒤 5분 동안 사용하지
  않으면 만료하며, 재확인은 이 유휴 기한만 연장한다. 재검사 예정 시각과 과거 순회
  시각은 바꾸지 않는다. 최대 기록 수는 기존 4,096개다.
  부팅·PID·생성 시각·주소·볼륨·전체 파일 ID·파일 변경 시각이 맞아야 재사용한다.
  확인 실패, 다른 파일, 다른 프로세스 세대, 만료 시에는 최초 검사로 취급한다.
- 변경된 레이아웃 후보가 주기 검사에 밀리지 않도록 접수 한도를 총 160개로 하고
  그중 32개를 예약한다. 주기 검사는 기존처럼 총 대기 128개부터 원본에서 보류한다. 기존 항목의
  병합과 FIFO 순서는 유지하며, 보류된 후보의 관측 시각이나 30초 유효기간을
  갱신하지 않는다.

이미지 작업 상한 2,048개, 감시 예약 256개, 25ms 순회 예산, 페이지·게시 상한과
실제 바이트 검증 조건은 유지했다. 순회 이력은 스케줄링에만 사용한다. 새 작업의
비교 바이트·완료 횟수·판정은 복원하지 않는다. 미관측 매핑 재사용을 식별하거나
현재 메모리의 정상성을 보증하는 이력이 아니다.

## 재현 조건과 측정

설치된 MSVC `14.44.35207`의 실제 32비트 vctip을 사용한다. `release-a`까지는
`Hostx86/x86/cl.exe`로 생성했다. `idle-a`·`idle-b`는 컴파일러 재시도에서 프로세스가
생기지 않아 같은 설치 경로의 VCTIP.EXE를 인자 없이 직접 실행한다. SHA256
`b69570b1bf2e28ef48f8b322249c9026b15be73b655b6b8f80279c87c299e613`을 확인하고
동일한 두 실제 뷰가 존재해야 시작한다. 실행 방법 차이를 완전히 동일한 프로세스
활동으로 간주하지 않는다. 매 실행 전후 `tools/validate-kmon-vctip.py snapshot`으로 두 실제 뷰를
독립 비교한다. 대조군은 13개(양성 9·음성 4), 관찰 시간은 모두 600초다.
대조군의 자식 `conhost.exe` 13개도 기존 자식 감시 정책으로 승격되므로 실제 감시
목록은 vctip을 포함해 27개다. 이 자식들을 제외하거나 감시 정책을 완화하지 않았다.

```powershell
tools/validate-kmon-live.ps1 -AllProcessLayouts -ImageSweepFixtures -SecondaryViewFixtures -ObservedProcessId <PID> -ObserveSeconds 600 -ProbeDriver -RequireQueueHealth -RequireCompletedWork -RequireImageCompletion -RequireLayoutNameAccounting -RequireFreshLayouts -OutputDirectory <new-directory>
python tools/validate-kmon-vctip.py audit --run <run> --before <before>/snapshot.json --after <after>/snapshot.json
```

`-SkipFixtures`는 사용하지 않는다. KMON 세션은 한 번에 하나씩 실행하고 관찰 중에는
빌드나 대규모 오프라인 분석을 하지 않는다. 대조군 바이너리 SHA256은 모든 실행에서
`ADEE3A4C4DCE154BDFA3A80618361F7E34B6930B41E3A2603179C5A1D2944B67`이다.
기준 모니터 SHA256은 `9CFE4E1DA63D936D3842F529E9C6C0DC99626E0A396B0448E6DF038C58BDBF21`,
중간 수정본은 `D2FB415C88BD6D3B36FBED85C76A29815821B0A702E4D5540E0353A1A8F1F361`,
차례 대여까지 적용한 중간 수정본은
`9BACCBC1210D28A34C4A120072EE9142BDBC873446DDA3C0DE7B2FFCD61EDB9F`,
주기 후보 한도를 96개로 낮췄던 중간 수정본은
`6E46B67438BE713827996359C81510E71FB01599D3D1953DC52E4F9E5D5AB2C8`이다.
주기 접수 128개와 변경 후보 예약 32개를 적용한 중간 수정본은
`4351D01108CB6D99E423F02468D83168889E0C1E6FC668BC9828F6E178931926`이다.
이력 유휴 만료까지 적용한 최종 수정본은
`B0A7E60EC5D2C4DFC415B00B707C4338217B3CB0F834427423DBA0FDF67ACF9F`이다.

배경 비교량은 `coverage.region` 중 `source=executable_page_compare`의
`compared_ranges`를 부팅·PID·생성 시각별로 합쳐 중복 주소를 제거한다. 반복 비교 횟수나
현재 캐시의 남은 페이지 합계로 검사 범위 증가를 주장하지 않는다. 실행 간 비교는
두 실행에서 식별된 배경 프로세스 세대만 대상으로 하며, `coverage.layout` 등에
식별자가 있지만 비교 바이트가 0인 세대도 포함한다. 비교에 성공한 세대만 교집합으로
택하면 검사량이 0으로 퇴행한 프로세스를 숨길 수 있기 때문이다. 프로세스 안의 미관측
매핑 교체를 구별하는 측정은 아니며, 전체 호스트의 미검증 바이트 분모도 아니다.
감시 분류에는 콘솔에 기록된 감시 PID 목록의 합집합을 사용해 대조군의 자식도
포함한다. 이 실행에서는 대조군 가족이 최종 drain까지 유지되며, 일반적인 PID
재사용을 추적하는 별도 원장으로 이 집합을 취급하지 않는다.

사라지지 않는 반례 테스트도 통과했다.
이전에 순회를 마쳤지만 마지막 캐시에서 과거 이력과 현재 완료 횟수가 모두 사라진
이미지는 `release-a`의 34개에서 두 실행 모두 0개로 줄었다. 배경에 빌려준 차례는
각각 386회·439회이며 감시 재검사도 304회·322회 진행했다.

전후 스냅샷은 각 뷰의 실행 범위 3,414,016바이트와 HIGHLOW 재배치 슬롯 9,129개를
독립 정규화하여 차이 0을 확인한다. 실제 KMON 완료 이벤트도 비교 바이트가 요청량과
같고 실패·제외·남은 페이지와 해당 뷰의 코드 변경 이벤트가 0이어야 한다.
대조군에서 확인한 58개 이미지 순회에는 작은 선언된 제외 구간이 있는 가져온 DLL도
포함된다. 여섯 합성 보조 뷰는 각각 8,192바이트를 전부 비교한다.

`idle-a`의 추가 관측은 실제 vctip `clr.dll` 한 페이지의 229바이트 차이,
다른 프로세스 두 개의 `ntdll.dll` 두 페이지(각각 128·32바이트), 실행 중인
`node.exe`와 `skia.node`의 PE 식별자 차이다. 저장한 예상·관측 페이지 및 PE 필드를
독립 계산으로 대조했다. 실제 바이트 차이라는 관측을 유지하며 악성 여부나 변경
주체를 확정하지 않는다. `idle-b`는 같은 CLR 차이와 USER32의 16바이트 차이,
같은 두 PE 식별자 차이를 확인했다. 두 실행에서 저장한 캡처 조각 6,449개·5,819개
(26,333,520·23,758,896바이트)도 검증했다. 이름을 근거로 숨기는 예외는 추가하지 않았다.

공통 캡처 읽기 실패 12,288바이트는 `driver_image` 캡처다. `idle-a`의 추가
106,496바이트는 `orphan_wx` 커널 주소 캡처 24건에서 발생했다. PID 11536은 이
스캔의 주소 공간 기준 PID이며, 실패 주소는 사용자 보조 뷰가 아닌 커널 주소다.
이 별도 커널 캡처의 공백을 실제 System.Data.dll의 실패 0과 합쳐 해석하지 않는다.

양성 대조군의 `idle-a` 최초 탐지는 0.74~174.83초였다. 항목별 지연이 일률적으로
줄지는 않았다(`orphan-image`: 기준 97.06초, `idle-a` 174.83초, `idle-b` 195.66초).
`idle-b`의 양성 최초 탐지 범위는 1.02~195.66초다. 음성 대조군 4개와
양성 9개에 대한 결과이며, 임의의 짧은 실행이나 호스트 전체의 누락·오탐 0을
보증하지 않는다. 접근 불가 프로세스, 읽기 실패, 이미지 등록 보류, 제외 구간과
미완료 순회도 계속 명시한다. 서로 다른 시점의 실행이며 캐시 상태·일시적 프로세스·
실제 vctip 실행 방법이 달라 전체 성능에 대한 통계적 보증으로 사용하지 않는다.

중간 `candidate-a`는 실제 두 뷰와 13개 대조군을 통과했지만 공통 배경 194개 프로세스
세대에서 비교한 주소 바이트가 931,647,016에서 887,721,400으로 4.7% 줄었다.
감시 최초 순회가 끝난 뒤에도 감시 재검사가 그 몫을 사용하던 원인을 추가로 확인하여
차례를 빌려 주는 정책을 넣었다. 중간 결과와 원본 캡처는 최종 결과와 별도로 보존했다.

차례 대여만 적용한 `final-a`·`final-b`에서도 실제 두 뷰는 전부 비교했다.
공통 배경 주소 비교량은 각각 기준 대비 +1.2%·-1.5%로 실행 간 변동이 있었다.
`final-b`는 변경된 `alias32-reloc` 후보가 원본에서 30,078ms, 접수 큐에서
1,578ms 기다려 31,656ms에 거절됐다. 대조군의 후속 탐지는 모두 성공했지만
`-RequireFreshLayouts` 및 이를 포함하는 실제 이미지 게이트는 실패했다.
이 실패를 통과로 바꾸거나 유효기간을 늘리지 않고 변경 후보 예약을 추가했다.

기존 128개 안에서 변경 후보 32개를 예약한 `validated-a`는 두 실제 뷰와 모든
엄격 게이트를 통과했지만, 공통 배경 193개 세대의 비교량이 931,647,016에서
579,138,736바이트로 줄었다. 레이아웃 확인량도 `final-a`의 98,650건에서
56,155건으로 감소했다. 빌드 후의 유휴 MSBuild 노드는 두 실행 모두에 있었으며
캐시·프로세스 상태까지 완전히 동일하다고 단정하지 않는다. 최종 정책은 주기 접수 한도를 128개로
복원하고 변경 후보 32개를 추가하여, 총 160개를 상한으로 제한한다. 원본 보관,
병합, 손실 회계와 30초 유효기간은 유지한다.

`release-a`는 레이아웃 확인량이 91,708건으로 회복되고 모든 엄격 게이트를
통과했지만 공통 배경 비교량은 875,446,584바이트로 기준보다 6.0% 적었다.
순회 뒤 재생성된 배경 이미지 34개는 과거 순회 기록이 있는데도 마지막 캐시에서
현재 완료 횟수와 `prior_traversal_ms`가 모두 0이었다(과거 순회 후 351,782~615,219ms).
고정 5분 이력이 사용 중에도 만료되는 경로를 보완해, 파일 식별자가 재확인된 이력은
유휴 만료만 연장하도록 했다. 이 이력을 현재 검증 결과로 복원하지는 않는다.

## 자체 테스트와 판정 범위

Release 빌드와 `KnLiveDbg.exe --self-test all`을 통과했다. 파이프라인 테스트는
재검사만 필요한 프로세스 13개와 최초 순회 프로세스 하나를 함께 두고 104차례를
선택한다. 최초 순회는 78차례를 받고 13개 재검사 프로세스도 모두 차례를 받는다.
개별 이미지 차례를 초기화해도 이 배분은 유지된다. 대기 중인 작업의 제외, 준비된
다른 종류로의 전환, 별도 배경 재검사 몫도 검사한다.
차례 대여 검사에서는 64차례 중 감시 재검사 12·배경 최초 순회 52(그중 대여 36)를
확인한다. 감시가 사라지면 배경만으로 32차례 중 최초 24·재검사 8을 받는지도 확인한다.

캐시를 비우고 같은 파일을 별칭으로 재등록하면 과거 순회 시각만 복원되며 현재
비교량·완료 횟수는 0이어야 한다. 읽기를 거절한 재검사는 `OwnedUnverified`여야 한다.
프로세스 재사용, 다른 주소·파일, 전체 파일 ID 변경, 이력 만료, 기록 상한도 확인한다.
계속 재발견된 이력이 원래의 만료 시각을 지나도 유지되는 동안 재검사 예정 시각,
과거 순회 시각, 현재 비교량과 완료 횟수가 바뀌지 않는지도 확인한다.
레이아웃 접수 테스트는 주기 후보 128개 뒤에 추가 주기 후보가 보류되어도 변경 후보
32개를 더 받을 수 있는지, 160개에서 추가 변경 후보가 보류되는지 확인한다.
병합은 포화 상태에서도 가능하고, FIFO 순서·원래 관측 시각·손실 0이 유지되어야 한다.
이 테스트는 실제 KMON·대조군·전후 스냅샷 검증을 대신하지 않는다.
