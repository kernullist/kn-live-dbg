# 2026-10-23 KMON 큐 포화 및 손실 개선

[앞선 실검증](KMON_LIVE_VALIDATION_20261023.md)의 layout 큐 포화와 수집 손실
31건을 조사했다. 큐 용량을 늘리지 않고 반복 후보 병합, 검사 사이의 대기 작업
처리, 정적 참조의 순환 접수를 적용했다. 최종 빌드를 동일한 6개 대조군으로
각각 180초씩 두 번 실행했으며 기대 탐지를 유지하고 검사한 큐 손실은 모두 0이었다.

## 확인한 원인

1. Layout 수집기는 프로세스당 주기적으로 최대 8개 후보를 보냈지만, 검증은
   여러 긴 스캔이 모두 끝나는 주기마다 최대 16개만 처리했다. 같은 매핑의
   반복 관측도 개별 작업으로 쌓였고, 30초가 지난 후보는 검증 전에 거부됐다.
2. 실행 참조 소비는 전체 주기당 최대 32개였다. IAT 등 대량 정적 소스가
   1,024개 큐를 먼저 채워 다른 참조도 탈락했다. 수정 전 계측 실행에서는
   IAT 접수 실패 70,015건, 전체 참조 탈락 78,327건, 만료 128건을 기록했다.
3. JSONL의 `lost_events`에는 내부 TI/live 분석 큐 손실이 포함되지만 콘솔
   `lost`는 원본 연속성 손실만 출력했다. 기존 31건 발생 구간에서 콘솔은
   0이었다. 따라서 내부 분석 큐 손실로 좁힐 수 있으나, 당시 로그에는 TI와
   live의 개별 카운터가 없어 어느 쪽의 31건인지는 소급 확정할 수 없다.

별도 계측 실행에서는 수집 손실 31건 자체가 재현되지는 않았다. 손실은 간헐적이며,
아래 표의 실행별 수치를 그대로 보존한다. 백그라운드 프로세스 활동도 실행마다
달랐으므로 이 결과를 고정 처리량이나 지연 보장으로 해석하지 않는다.

## 변경

- 동일 프로세스 세대·영역·할당·속성·이미지 경로의 미처리 layout 후보는
  최신 관측으로 합치고 원래 FIFO 위치를 유지한다. 속성이 다른 후보와
  layout 변화 이벤트는 병합하지 않는다. 병합 횟수와 실제 탈락을 구분한다.
- 기존 스캔 경계와 사용자 모듈 경계에서 수집 이벤트, layout 및 실행 참조를
  처리한다. 검증 상태는 기존 분석 스레드에 유지해 공유 상태의 병렬 변경을
  도입하지 않았다. 재진입을 막고 항목 사이에서 시간 예산을 확인한다.
- 정적 IAT/모듈 테이블의 코드 경로 검증은 16개씩, 주요 커널 참조 테이블은
  64개씩 위치를 순환한다. 대기 참조가 256개 이상이면 접수하지 못한 위치를
  보존한다. 기존 표면 스캔과 직접 이상 판정은 계속한다. 사용자 커서는
  PID·생성 시각·모듈별로 분리하며 제한 용량의 퇴출도 기록한다.
- 콘솔 손실 합계를 JSONL과 맞추고 원본 연속성, TI/live 큐별 탈락·최대 점유,
  참조 접수·처리·만료, layout 병합 지표를 추가했다.
- `validate-kmon-live.ps1 -RequireQueueHealth`는 대조군 탐지 및 캡처 검증에 더해
  이벤트 손실, layout/참조 탈락, 캡처·저장·진단·카탈로그 큐 탈락과 커서 퇴출이
  0이어야 통과한다. 참조 만료는 참조 탈락에 포함된다.

## 반복 실행 중 발견한 소유권 오탐

수정 전 계측 실행의 정상 `hold`, 중간 후보 빌드의 `mapped-readonly`에서 각각
정상 DLL의 추가 실행 페이지 3개가 `unowned_executable`로 분류됐다. 이 실행들은
실패로 보존했다. 해당 페이지들은 보고된 모듈 크기 밖에 있지만 현재 `MEM_IMAGE`
할당의 기준 주소와 backing 파일이 로더 모듈과 같았다.

현재 매핑과 모듈의 AllocationBase, 열린 파일의 volume serial/file ID,
재조회한 매핑과 경로가 일치하면 `owned_unverified`로 남긴다. 파일명이나
서명에 대한 예외 목록을 만들지 않았으며 바이트의 무결성을 인정하지 않는다.
연결된 로더 모듈이 없는 이미지 및 private 매핑에는 적용하지 않는다.
최종 실행에서는 해당 기록이 `coverage.executable_memory`로 남았다.

판정에 사용한 필드의 의미는 Microsoft의
[MEMORY_BASIC_INFORMATION](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-memory_basic_information)과
[FILE_ID_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_id_info)를 확인했다.
추가 페이지의 생성 원인을 특정 패치 기술로 단정하지 않았다.

## 회귀 및 남은 범위

Release 빌드와 `--self-test all`을 통과했다: timeline 28, MCP catalog 89,
console 557, commands 2,961, remote protocol 66 및 connect 인수 검사.
회귀에는 반복 후보 1,000개 병합, FIFO 유지, 실제 용량 초과, 순환 검사의
꼬리 도달, 대기열 차단 시 커서 유지와 소스 축소를 포함한다. 소유권 검사는
실제 자체 이미지와 private 매핑, 누락·다른 backing 파일을 대조했다.

`validate-kmon-core.ps1 -Sanitize`도 통과했다. ASan을 적용한 standalone 핵심
엔진에서 hunting 11,326개, pages 54개, FP 49개 및 이미지·큐·정체성 검사를
통과했다. 최종 두 실행의 EXE SHA-256은 동일하며 테스트 프로세스와 드라이버
서비스가 모두 종료된 상태를 별도로 확인했다. `git diff --check`도 통과했다.

전체 호스트 검사 범위는 여전히 partial이다. 최종 A/B에는 일반 캡처 읽기 실패
11/14건과 위 미완료 작업이 남아 있다. 동적 소스의 모든 단기 참조나 모든 주소의
검사 완료를 보장하지 않는다. 큐 용량을 초과하는 다른 부하에서도 무손실이라는
보장은 하지 않으며, 새 지표와 강화 실행 조건으로 다시 검증할 수 있다.

```powershell
.\tools\validate-kmon-live.ps1 -ObserveSeconds 180 -ProbeDriver -RequireQueueHealth
```
