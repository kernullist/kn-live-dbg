# KMON 후보 유효기간·이미지 이름 수집 검증 (2026-10-23)

기준 커밋은 `789368c`다. 이전 [전체 프로세스 큐 검증](KMON_ALL_PROCESS_LAYOUT_VALIDATION_20261023.md)에
남은 후보 만료와 이미지 이름 수집 실패를 같은 테스트 PC에서 분석했다.
원본 실행 증거는 `.build/kmon-layout-freshness-20261023`에 보관했다.

## 원인과 변경

### 이름 수집

기존 전체 이름 한도 16,384개는 초기·최신·진행 중 스냅샷에 중복 보관되는 경로를
모두 합산했다. 짧은 경로가 대부분이어도 항목 한도에 먼저 도달했고, 용량 부족은
동일 이미지의 여러 영역에서 반복 집계됐다. 첫 영역이 예약 영역이면 실패한 빈
이름을 캐시해 이후 커밋 영역에서 다시 질의하지 않는 문제도 있었다.

- 이름 항목 한도를 65,536개로 조정하고, 널 문자를 포함한 실제 문자열 길이 합계에
  16,777,216 wchar 한도를 추가했다. 문자열 내용 최대 32 MiB는 이전 최악값과 같다.
  컨테이너·할당자 비용까지 포함한 전체 힙 한도라는 뜻은 아니다.
- 스냅샷별 512개 한도는 유지한다. 성공한 이름만 보관하고, 실패는 고유 이미지
  할당별 한 번 집계한다. 용량 부족·API 오류·경로 잘림·커밋 영역 부재를 분리한다.
- 첫 커밋 영역에서 이름을 질의하며 예약 영역을 먼저 봤다는 이유로 실패를 고정하지
  않는다. 매 스냅샷에서 새로 조회하므로 오래된 이름을 다음 관측에 복사하지 않는다.
- 1,024자 버퍼가 부족하면 32,768자로 재시도한다. 반환 길이가 버퍼 크기와 같으면
  잘린 결과로 처리하며, 후보 재확인에도 같은 함수를 사용한다.

버퍼 크기 반환을 성공한 전체 경로로 취급하지 않는 처리는
[Microsoft GetMappedFileNameW](https://learn.microsoft.com/en-us/windows/win32/api/psapi/nf-psapi-getmappedfilenamew)의
계약을 확인했다. 실제 장치 볼륨 경로와 기존 생성 시각·매핑·이름 재확인을 유지한다.

### 후보 대기 시간

사용자 프로세스 심층 검사는 최대 8개를 선택하면서 16개마다 대기 작업을 처리하도록
되어 있어 실제로 양보하지 않았다. 이를 대상 사이 처리로 바꿨다. 여러 독립 검사를
연달아 수행하던 경계에서도 대기 작업을 처리하고, 이벤트 수신 전에 레이아웃 후보를
먼저 한 조각 처리한다.

첫 수정본 `candidate-a`에는 주기적 후보 만료 39건이 남았다. 최대 큐 대기 28,625ms,
최대 처리 호출 간격 21,719ms였다. 만료 기록에는 원본 관측부터 접수까지 약 2.7초,
큐 안에서 약 28초 기다린 사례가 포함됐다. 이름 수집만 개선하면 늘어난 검증 작업이
작은 소비 예산을 다시 압박할 수 있었다.

최종본은 대기가 64개 이상이면 처리 조각을 최대 64개·100ms로 늘린다. 그 외에는
16개·25ms이며, 접수 한도 128개와 원본 보관·순환 커서를 유지한다. 30초 만료를
늘리거나 오래된 후보의 관측 시각을 갱신하지 않는다. 개별 API 호출은 강제 중단하지
않으므로 시간 예산은 호출 경계에서 적용한다. 큐 대기·원본 대기·최대 처리 간격과
그 뒤 경계를 별도 계측한다.

이 단계의 `final-a`는 만료 0건이었으나 `final-b`에서 309건이 재발했다. 최대 처리
간격은 `after_hook_callbacks` 직전 28,781ms였다. 콜백 수집 7개 종류와 최대 64개
진입점 확인을 한 번에 수행하던 경로를 나누고, 종류별 일관성 검사가 끝난 뒤와
진입점 8개 사이에서 대기 작업을 처리하게 했다. 미완성 목록이나 잠금을 넘기지 않는다.

`final-c`는 만료 0건으로 통과했지만 객체 콜백 수집 하나에 최대 18,484ms 공백이
남았다. 코드를 확인하니 사전 검사에서 이미 확인한 동일한 커널 PDB 구조를 객체
종류마다 다시 계산하고 있었다. 최종본은 한 수집의 검증된 구조 정보를 공유한다.
프로세스·객체 목록이나 콜백 값을 캐시하는 변경은 아니며, 종류별 목록·링크·레코드와
모듈 문맥은 계속 직접 읽는다. 이 수정 뒤 최종 바이너리를 다시 빌드해 반복했다.

### 확장된 수집이 드러낸 보조 이미지 뷰

`candidate-a`는 Visual Studio `vctip`의 `System.Data.dll`에서 새 코드 변경 기록을
남겼다. 캡처와 직접 메모리 질의를 대조한 결과 같은 파일이 `0x07dc0000`과
`0x6e3e0000`에 매핑되어 있었고, 두 뷰의 PE ImageBase와 첫 페이지 포인터는 모두
실제 로더 주소 `0x6e3e0000`을 가리켰다. 보조 뷰 주소로 정규화한 기대값이 틀렸다.

디스크의 HIGHLOW 재배치 18개를 실제 로더 주소로 독립 재계산하면 차이 36바이트가
모두 사라졌고, 캡처와 재계산 페이지의 SHA-256도 일치했다. 증거는
`candidate-a/system-data-views.json`, `system-data-relocation-audit.json`과 해당 원본
캡처다. 이 관측은 파일 전체의 정상성 또는 최초 section 출처 증명이 아니다.

최종본은 메모리 ImageBase가 디스크 선호 주소·현재 매핑 주소와 모두 다르면
`live_image_relocation_base_ambiguous`로 검증을 보류한다. 제3의 헤더 주소를 신뢰해
정상으로 승인하거나 재배치 슬롯을 일괄 제외하지 않는다. PE/PDB 식별자 변조와
읽기 실패는 기존 별도 사유를 유지한다. 이 보조 뷰의 바이트 검증은 남은 공백이다.
`final-b`의 실제 KMON에서도 같은 PID·뷰 주소가 이 사유의 coverage로 기록됐고
코드 변경으로 보고되지 않았다.

## 검증 방법

```powershell
tools/build.ps1 -Configuration Release
x64/Release/KnLiveDbg.exe --self-test all
tools/validate-kmon-core.ps1 -Sanitize
tools/validate-process-layout.ps1 -Sanitize
tools/validate-kmon-live.ps1 -AllProcessLayouts -ImageSweepFixtures -ObserveSeconds 300 -ProbeDriver -RequireQueueHealth -RequireCompletedWork -RequireImageCompletion -RequireLayoutNameAccounting -RequireFreshLayouts
```

전체 프로세스 모드로 시작한 뒤 소유한 대조군을 감시 목록에 추가한다. 양성 5종,
음성 2종과 고정 이미지 28개 완료 조건은 이전과 같다. 새 옵션은 각 완료 스냅샷에서
`알려진 이름 + 실패 = 이미지 할당 수`, 실패 분류 합계·API 오류 합계, 이름 보관량을
검증한다. 만료 카운터와 영속 거절 기록도 일치해야 한다.
`-RequireFreshLayouts`는 전체 프로세스 범위·접수 장부 확인과 후보 만료 0건을 추가 합격 조건으로 둔다.

최종 Release 전체 자체 테스트와 핵심·레이아웃 ASan 검사가 통과했다. 레이아웃
검사는 105,080개 확인에서 실패 0건이다. 이름 용량·문자 한도·중복 실패·예약 영역
후 커밋 영역·실제 이름 질의 실패·긴 이름·최대 버퍼 잘림을 검사했다. 재배치 검사는
PE32/PE32+의 디스크 선호 주소·정상 로드 주소·제3 주소를 구분한다. 실제 소유한
`SEC_IMAGE_NO_EXECUTE` 보조 뷰에서도 모호성을 재현하고, 정상 로드 이미지는
참조 자격을 유지하며 타임스탬프 변조는 여전히 식별자 불일치로 검출했다.

초기 ASan 레이아웃 검사에는 보조 뷰도 항상 정상 참조라고 기대하던 기존 단언 하나가
실패했다(`layout-asan-b.log`). 실제 헤더 주소에 따른 기대를 명시하고, 보조 뷰가
정상·변조 어느 쪽으로도 승인되지 않는 확인을 추가한 후 통과했다(`layout-asan-c.log`).

따른 변동을 보여 주지만, 이번 결과를 그 수치만으로 개선율로 표시하지 않는다.

### 배경 프로세스 관측의 별도 확인

두 최종 실행의 `node.exe`·`skia.node` 식별자 불일치는 캡처 메타데이터를 직접
해석해 재확인했다. Node는 타임스탬프·진입점·이미지 크기·체크섬, skia는 체크섬이
현재 경로의 파일과 실제로 달랐다(`identity-audit.json`). 최초 section 파일 객체의
출처는 확인하지 못했으며, 기록은 `observation`·`maliciousness=not_established`다.

`final-e`에서는 `vctip` PID 5740의 `clr.dll`에 코드 바이트 변경 관측 1건이 추가됐다.
기준 주소 `0x73da0000`, RVA `0x12000` 페이지의 디스크 재배치를 독립 재계산했을 때
기대 캡처와 정확히 일치했고, 실제 관측과는 229바이트가 달랐다. 이는 보조 이미지
뷰에서 발견한 정규화 계산 오류와 다르다. 기대·관측 캡처 ID는 420·419다.

변경 중 21바이트는 세 x86 TLS 접근 코드, 204바이트는 여섯 레지스터용 34바이트
GC 쓰기 장벽 코드 형태였다. 공식 .NET 소스도 이 영역을 CC 패딩으로 예약한 뒤
실행 중 코드를 복사하고 레지스터·주소를 채우는 동작을 보여 준다.
([예약 영역과 코드 형태](https://github.com/dotnet/coreclr/blob/master/src/vm/i386/jithelp.asm),
[런타임 복사와 패치](https://github.com/dotnet/coreclr/blob/master/src/vm/i386/jitinterfacex86.cpp))
이 비교는 정상 런타임 초기화와 부합한다는 추론이며, 해당 .NET Framework 바이너리의
정확한 소스 대응이나 변경 주체를 증명한 것은 아니다. 남은 RVA `0x12ba8`의 4바이트
변경 주체도 확정하지 않았다. 관측을 숨기거나 정상으로 승인하지 않고 악성 미확정
상태로 보존했다. 독립 재계산·범위·해시는 `final-e/clr-audit.json`에 기록했다.

## 결과 해석과 남은 범위

이름 수집 성공은 그 이미지 전체의 바이트 검증 완료와 다르다. `checked`도 후보 매핑
재확인 횟수다. 완료 스냅샷은 원자적 관측이 아니며, 접근 불가 프로세스·매핑 변경·
프로세스 종료는 별도 미검증 기록으로 남는다. 이 실험은 통제한 양성·음성 대조군에
대한 탐지와 실제 호스트의 수집·대기 상태를 검증한다.

최종 두 실행에서 프로세스 질의 불가 상태가 각각 13·14개 남았다. 캡처 계층의
실제 읽기 실패는 12,288·180,224바이트, 사전에 확인한 읽기 불가 범위는 각각
344,064바이트였다. 이는 이름 수집 실패나 큐 유실과 별개이며 검증 성공에 포함하지
않는다. 대조군 이미지 순회 완료에도 기존 동적 재배치 제외 구간은 명시적으로 남는다.

전체 프로세스 모드에서도 이미지 작업 캐시, 페이지 예산과 순환 검사가 있으므로
모든 배경 이미지의 전체 바이트가 300초 안에 끝난다는 주장은 하지 않는다. 보조 뷰의
재배치 기준 모호성은 새로 드러내는 coverage gap이며 정상 판정으로 바꾸지 않았다.
기존의 동적 재배치 제외 구간과 접근 불가 페이지도 계속 명시한다.
최종 `image_traversed_items=0`은 2,048개 작업 캐시에 남은 항목의 순간 집계다.
완료 항목이 다른 배경 작업을 위해 퇴출될 수 있어 누적 완료 수로 쓰지 않았다.
대조군 28개 완료는 영속 이벤트로 확인했으며, 두 실행 종료 시 캐시에 기록된 남은
이미지 페이지 2,251,431·2,472,539개는 이번 완료 범위에 포함하지 않는다.
