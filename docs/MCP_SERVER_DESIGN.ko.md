# MCP 구현 구조

[English](MCP_SERVER_DESIGN.md) · [설정](MCP_SETUP.ko.md) · [도구 목록](MCP_TOOL_REFERENCE.md)

이 문서는 현재 구현을 설명한다. 이전 단계별 계획과 초기 scaffold 설명은
제거했다. `user/McpServer.cpp`는 HTTP.sys·인증·JSON-RPC·목록·큐를,
`user/main.cpp`의 `RunMcpEngineLoop` / `DispatchMcpRequest`는 커널·심벌
작업과 결과 생성을 담당한다.

## 실행 경계

현재 `main`에서 운영자가 실행 중인 컨트롤러에 `mcp on --observe`를 입력하면
루프백 전용 조회 세션이 열린다. 리스너는 인증과 본문 처리 전에 실제 연결의
양쪽 IP 주소를 확인한다. `mcp status`, endpoint 파일, `kn://capabilities`에서
`observe`, `observe_source`, `legacy_write_locked`, `legacy_write_enabled` 중 현재 범위를 확인할 수 있다.

| 공유 비밀번호 조회 세션 | 허용 범위 |
| --- | --- |
| 도구 | `operations.get`, `timeline.status`, `timeline.query`, `graph.query`, `ti.subscribe`의 기본 동작 또는 `status` |
| 리소스 | `kn://capabilities`, `kn://session/info`, `kn://drivers/status`, `kn://ti/stats` |
| 프롬프트 | 빈 목록 |

범위를 벗어난 요청은 큐에 들어가기 전에 거부하므로 작업 ID가 생기지 않는다.
엔진은 실행 직전에도 같은 권한을 검사한다. 타임라인과 그래프는 보관된 이벤트를
직접 조회하며 기본 50건, 최대 64건을 선택한다. 일치 여부를 확인하려면 전체
저장소를 훑을 수 있다. 드라이버 상태는 기존 장치와 서비스에 질의할 수 있다.
조회 세션의 감사 로그에는 요청 인자·미허용 식별자·프로토콜 세션 ID·응답 본문을
기록하지 않는다. 조회 결과에는 보관된 이벤트의 원본 필드가 포함될 수 있다.
이 권한은 리스너를 종료할 때까지 같은 자격 증명을 쓰는 클라이언트에 공통 적용된다.

```text
HTTP 요청 -> 본문 크기 / 인증 / 세션 / JSON 검사
          -> typed 인자 검사 -> FIFO -> 메인 엔진
          -> result promise -> HTTP 응답
```

리스너는 DeviceClient나 DbgHelp를 직접 호출하지 않는다. 엔진이 작업을 직렬화하고
출력 캡처를 소유한다. 활성화 중 로컬 콘솔은 `off`, `status`만 받는다.
MCP와 remote는 별도 큐를 가지며 동시에 listen할 수 없다. 공용 우선순위
EngineQueue를 구현한 것은 아니다.

큐는 대기 작업 8개까지 수용한다. 30초 응답 대기가 실행 전에 끝나면 큐에서
작업을 제거한다. dispatch 뒤에는 작업이 계속될 수 있고 클라이언트의 결과는
불명확하다. 실행 중인 호출을 rollback하지 않는다. stop은 대기 작업을 취소하고
control/engine 종료 경로로 리스너를 join한다. 취소 알림은 범용 작업 취소 기능이 아니다.

엔진 큐에 수용된 작업은 JSON-RPC 요청 ID와 별개인 128비트 `operation_id`를 받는다.
비공개 `kn.mcp_operation.v1` 메타데이터를 도구 응답의
`_meta["knlivedbg/operation"]`와 추가 텍스트 항목으로 반환한다.
기존 `structuredContent`와 첫 텍스트 항목은 유지한다. 리소스 성공 응답은
같은 `_meta`, 오류는 `error.data`에 담고 요청 감사에도 응답 시점 상태를 기록한다.
`operations.get {"operation_id":"<반환된 ID>"}`는 리스너에서 바로 조회하므로
실행 중인 엔진 작업을 기다리거나 재등록하지 않는다.

상태는 `queued`, `running`, `cancelled_before_execution`, `succeeded`,
`failed`, `unknown_outcome`이다. 실행 뒤 시간 초과는 엔진 반환 전까지 활성
기록으로 남으며, 처리되지 않은 엔진 예외는 종료되어도 결과 불명으로 남는다.
`operation_finished`는 실행 전 취소도 포함하지만 `engine_finished`는 실제
dispatch가 있어야 참이다. 성공/실패는 엔진의 오류 플래그이며 대상 부작용을
독립 검증했다는 뜻이 아니다. 시각은 수집기 부팅 기준 밀리초의 10진 문자열이다.

메타데이터는 최대 256개이며 오래된 종료 기록부터 교체한다. 모두 활성 작업이면
새 작업을 거절한다. 결과 본문은 저장하지 않는다. 기본 모드에서는 서버 재시작이 기록을 지우고
같은 서버의 재초기화는 유지한다. 공유 비밀번호로 접속하는 클라이언트는 영수증을
공유한다. 출처별 조회 모드에서는 소유권을 검사한다. `not_retained`는 실행 결과를 판정하지 않는다.
ID를 받기 전에 연결이 끊기면 요청 ID로 복구할 수 없다. 자동 재시도·멱등 재전송·
롤백·실행 중 취소·표준 MCP Tasks는 미지원이다. 별도 remote 프로토콜의
작업 조회도 아직 연결되지 않았다.

## 작업 기록 복구

처음에는 기존 로컬 상위 폴더 아래에 새 디렉터리를 지정해
`mcp on --observe --journal <directory>`로 시작한다. 재시작 후에는 같은
Windows 계정과 MCP 비밀번호로 같은 디렉터리를 연다. 새 클라이언트 세션을
초기화한 뒤 기존 작업 ID를 `operations.get`에 전달하면 최근 승인 256건 안에서
기록을 조회할 수 있다. 조회 한도는 새 리스너에서 다시 시작한다.

| 마지막 저장 단계 | 복구할 수 있는 상태 |
| --- | --- |
| 대기열 승인 | 실행 승인을 받기 전에 끝난 작업이다. 검사 건수와 결과 바이트는 0이며 중단 시각은 알 수 없다. |
| 실행 승인 | 엔진 반환 기록이 없어 `unknown_outcome`을 반환한다. 최종 차감량도 미확정이다. |
| 취소 또는 엔진 반환 | 취소, 성공, 실패, 예외 당시의 상태와 사용량을 복구한다. |

공유 비밀번호 세션의 영수증에는 `journal`에 주체 ID, 원래 컨트롤러 프로세스 세대, 승인 범위,
요청 HMAC-SHA-256과 승인·실행 승인·엔진 반환 시각이 들어간다. 시각 단위는
UTC FILETIME이고, 대상 효과를 검증한 시각은 `null`이다. 저장 파일은 Windows
DPAPI로 보호하며 디렉터리와 비밀번호에 연결한다. 요청 인수와 결과 본문은
저장 대상에서 제외한다. 일반 요청 감사 로그에는 작업 ID와 상태를 기록하고
요청 지문과 주체·컨트롤러 식별자는 제외한다. `journal_unavailable`을 받으면 같은 저널을 다시 열어
마지막 저장 상태를 확인한다. 복구 과정에서 작업을 자동으로 재실행하지 않는다.

한 디렉터리에는 한 리스너만 기록한다. 손상된 저널이나 잘못된 비밀번호로는
시작할 수 없다. 같은 비밀번호를 쓰는 클라이언트는 주체를 공유한다. 저장소
소유자가 과거 사본을 복원할 수 있으며, 쓰기 중 중단으로 남은 임시 파일은
복구에 사용하지 않는다.

## 출처별 조회 권한

`mcp on --observe --principal <fingerprint> <source>`는 클라이언트의 bearer
지문과 보관된 출처 하나를 연결한다. 루프백에서만 동작하며 `scope`는
`observe_source`다. 서버는 인증된 bearer로 세션과 조회 권한을 결정한다.
클라이언트가 `initialize`를 다시 호출하면 자신의 세션 ID만 교체된다. 최대
16개 주체를 설정할 수 있고, 각 누적 한도는 증거 조회가 허용된 주체끼리 균등하게 나눈다. 재접속 후에도
같은 리스너에서는 기존 잔여량을 적용한다.

기본 권한에서 도구는 `timeline.query`, `operations.get`이며 리소스는 `kn://capabilities`다.
서버가 붙인 권한을 큐 등록과 엔진 실행 시점에 검사한다. 타임라인은 대소문자를
구분하는 출처 인덱스를 사용한다. 조회 건수, 검사 비용, `total_stored`는 해당
출처에 속한 행으로 계산한다. `kn.mcp_source_timeline.v1`은 FILETIME 시각,
도메인, 동작, PID, TID, 대상 PID를 반환한다. 128 UTF-16 코드 단위를 초과하는
도메인이나 동작은 `null`이다. 원본 증거, 전역 이벤트 ID, 그래프와 호스트 전체
통계는 이 범위에서 제공하지 않는다. 출처 표기의 신뢰도는 수집 경로에 달려 있다.
타임라인 저장 용량은 호스트에서 공유한다.

저널은 전용 키로 자격 증명 지문과 출처를 묶어 소유자를 기록한다. 상대의 작업 ID와
보관하지 않은 ID에 같은 `not_retained` 응답을 반환한다. 운영자는 별도 암호로
저널을 연다. 공유 암호 모드와 출처별 모드는 서로 다른 DPAPI 엔트로피를 사용한다.
최근 256개 영수증 보관 한도는 저널 전체에 적용된다. [클라이언트 설정](MCP_SETUP.ko.md)

## 증거와 작업 기록의 조회 권한

`--principal-access <지문> <evidence|operations|both>`로 지문별 조회 권한을 지정한다.
출처 또는 대상 지문을 선언하는 순서와 관계없이 적용한다. 같은 지문에 권한을 두 번 지정하거나
등록되지 않은 지문에 권한을 주면 리스너 시작을 거부한다. 기본값은 `both`다.
인증된 클라이언트는 `kn://capabilities`의 `observe_access`와 `tools/list`에서 자신의 권한을 확인한다.

| 권한 | 도구 | 범위 |
| --- | --- | --- |
| `evidence` | `timeline.query` | 허가된 행을 읽고 조회 예산을 사용한다. 성공·시간 초과·저널 오류 응답에서 작업 ID와 영수증을 제외한다. 운영자는 로컬 감사 기록으로 요청과 결과를 연결할 수 있다. |
| `operations` | `operations.get` | 알고 있는 ID로 본인의 보관된 영수증을 조회한다. 권한 목록에서 증거 출처 이름과 예산을 제외하며, 증거 예산을 배분하거나 차감하지 않는다. |
| `both` | 두 도구 | 허가된 행을 읽고 발급된 영수증으로 작업 상태를 다시 확인할 수 있다. |

현재 권한은 조회 가능 여부를, 영수증 소유자는 조회 가능한 기록의 범위를 결정한다.
운영자가 저널을 다시 열고 작업 조회를 허용하면 원래 지문·출처·대상 수명이 일치하는 과거 기록을 읽을 수 있다.
새 저널 항목의 `journal.approved_access`에는 접수 당시 권한이 남는다. 이 필드를 도입하기 전 기록의 기본 권한은 `both`였다.
메모리에서만 보관한 영수증은 리스너 재시작 시 만료된다. [설정 예시](MCP_SETUP.ko.md#증거-또는-작업-기록-허용하기)

## 프로세스 수명별 조회 권한

운영자는 클라이언트가 조회할 TI 기록을 한 프로세스의 실행 기간으로 제한할 수 있다.
수집기는 이벤트 헤더의 TI 공급자 GUID를 확인한다. 헤더의 PID에 대해 같은 프로세스 핸들로 생성 시각과 이미지 경로를 확인하고 부팅 ID를 기록한다.
저장소는 출처, 부팅 ID, PID, 생성 FILETIME이 일치하는 행만 집계하고 검색 비용을 계산한다.
재사용된 PID의 다른 실행 기록, 페이로드에 등장한 상대 PID, 가져온 행이 주장하는 식별자는 권한의 근거에서 제외한다.
가져온 행과 검증한 행의 표시 필드가 같아도 각각 보관하므로 출처 전체를 조회하면 둘 다 보일 수 있다.
마지막 검증 행이 퇴거되면 해당 프로세스 수명의 인덱스도 제거된다.

클라이언트는 `initialize` 후 `kn://capabilities`에서 `target_session`을 읽어
`timeline.query`와 `operations.get` 양쪽에 전달한다. 다시 초기화하면 본인의 두 핸들이 교체되고
잔여 한도는 유지된다. 리스너는 접수, 대기열 인출, 실행 직전, 결과 반환 시점에 권한을 확인한다.
대기 중 만료되면 HTTP 리스너는 엔진 반환을 기다리지 않고 다음 요청을 받는다.
엔진은 이미 검사한 행을 사용량에 반영한다. 정산 시 핸들이 만료되었으면 출력 비용은 0바이트다.
HTTP 전송부도 직렬화 후 다시 확인하므로 정산한 결과라도 만료되면 본문과 작업 ID를 전달하지 않는다.
결과 형식 `kn.mcp_target_timeline.v1`은 시각, 도메인, 동작, 이벤트 헤더 PID와 TID를 제공한다.

대상별 영수증의 `target_generation`은 프로세스 수명의 키 기반 해시이고
`controller_generation`은 요청을 접수한 컨트롤러 실행을 식별한다. 복구하려면
원래 지문·출처·프로세스 수명과 새 대상 핸들이 필요하다. 저널을 사용하지 않으면
리스너 종료 시 영수증의 보관 기간도 끝난다. [클라이언트 설정](MCP_SETUP.ko.md#한-프로세스의-기록만-허용하기)

## 조회 세션의 누적 한도

`mcp status` 또는 `kn://capabilities`의 `observe_budget`에서 한도와 사용량,
잔여량을 확인한다. 공유 암호 모드의 클라이언트들은 하나의 한도를 공유한다. 클라이언트가
`initialize`를 다시 보내도 잔여량은 유지된다. 운영자가 리스너를 종료하고
새로 시작하면 새 한도를 사용한다. 이전 작업은 명시적으로 다시 연 저널에서 조회할 수 있다.

| 항목 | 리스너당 한도 | 차감 시점 |
| --- | ---: | --- |
| 승인된 엔진 요청 | 128회 | 큐에 들어간 도구 호출이나 리소스 조회마다 1회 |
| 요청한 이벤트 | 1,024건 | 타임라인·그래프 조회가 승인될 때 지정한 건수. 생략하면 50건 |
| 검사한 이벤트 | 65,536건 | 상태 집계와 조회가 실제로 방문한 항목마다 1건. 한 요청에서 최대 4,096건이며 필터 불일치와 그래프의 다음 일치 항목 확인도 포함 |
| 결과 데이터 | 1 MiB | 엔진 결과의 텍스트와 구조화 JSON을 UTF-8로 환산해 각각 한 번 차감. 한 결과는 최대 64 KiB |

큐 진입 전에 거부된 요청은 차감하지 않는다. 큐에서 취소되면 승인 시 차감한
몫은 유지된다. 응답 대기 시간이 지난 작업이 뒤늦게 완료돼도 결과는 한 번만
계산한다. 이전 리스너의 작업은 새 리스너의 한도를 사용하지 않는다.
검사 한도로 범위 확인이 중단되거나 결과가 너무 크면 `budget_exhausted`와
원인 항목·단계를 반환한다. 부분 결과는 내보내지 않는다. 작업 조회 권한이 있는 클라이언트는
접수된 요청의 작업 ID를 받는다. 한도를 소진한 뒤에도 해당 권한으로 `operations.get`에서 결과 상태를
확인할 수 있다. 전송 부하, 임시 메모리, CPU 시간과 커널 I/O는 별도 측정 대상이다.

작업 영수증의 `observe_charge`에는 승인 시 차감한 몫이 즉시 표시된다.
실제 검사 건수와 결과 바이트는 작업이 끝날 때까지 `null`이고, 큐에서
취소되면 둘 다 0이다. 응답 시간이 초과된 뒤에도 `operations.get`에서
최종 사용량과 한도 거부의 항목·단계를 확인할 수 있다.

## 전송과 권한

- HTTP `/mcp`, 기본 모든 인터페이스의 51766, 선택적 loopback/특정 bind.
  TLS는 없다. MCP 프로토콜은 2025-06-18, 서버는 knlivedbg/0.1.0이다.
- 세션 비밀번호 bearer 인증과 초기화 뒤 `Mcp-Session-Id`를 사용한다.
  비밀을 포함한 보조 파일은 현재 사용자 DACL과 원자적 교체를 사용한다.
- 읽기 모드는 쓰기 도구를 숨기고 커널 gate도 끈다. `--allow-write`가 typed
  변경을 허용하며 읽기 목록에 있는 `ti.subscribe`의 start/stop도 이 권한이 필요하다.
- raw 콘솔/kd 도구는 없다. 콜백 변경은 협력형 fixture에만 허용한다.
  별도 process-protection 쓰기 도구는 명시한 PID도 지원한다.
- 현재 main은 커널 쓰기 모드 확인에 성공해야 엔진 작업을 실행한다.
  로컬 REPL 복귀 시 write-off를 요청하며, 실패하면 상태 미확인으로 보고한다.
  자동으로 쓰기를 활성화하지 않는다.

## 파싱과 결과

본문 상한은 1MiB다. 실패/불완전 본문은 HTTP 400, 초과는 413과 JSON-RPC
parse error를 반환한다. 잘못된 JSON은 HTTP 200 안의 JSON-RPC 오류로도 반환한다.
뒤쪽 데이터·해석 후 중복 키·잘못된 UTF-8·64단계를 넘는 중첩을 거부한다.
envelope와 도구 인자를 dispatch 전에 검사하며, schema가 string으로 정한
숫자는 문자열로 전달한다.

전송 오류와 도구 결과 오류를 구분한다. 일부 도구는 structured content,
일부는 텍스트를 반환한다. 기존 모드는 리소스 8개와 프롬프트 7개를 제공한다.
자동 요청 감사와 쓰기 감사는 별개다.

통일된 pagination/output schema, SSE 진행, 개별 쓰기 elicitation,
엄격한 protocol-version 헤더 검사는 미구현이다.
남은 작업은 [FEATURE_PLAN.md](FEATURE_PLAN.md)에 정리한다.

## 검증

`--self-test mcp-tools`는 드라이버 없이 목록·인자·dispatch 계약을 검사한다.
별도 `--self-test mcp-http`는 loopback 전송을 검사하며 HTTP.sys 등록 권한이 필요하다.
`--self-test mcp-observe`는 같은 포트에서 조회 범위, 실행 전 거부, 타임라인 응답과 감사 기록을 확인한다.
네트워크 fixture는 순차 실행한다. 실제 커널 동작·쓰기 검증·정리는
[수동 체크리스트](MANUAL_TEST_CHECKLIST.md)에서 따로 확인한다.
