# KMON 전체 이미지 순회 검증 — 2026-10-23

최종 동일 빌드의 180초 실험 두 번에서 고정 이미지 집합 28개를 모두 순회했다.
기준의 7/28개에서 28/28개로 늘었으며, 꼬리 변조를 포함한 대조군 7개와
수집·검사 큐 무손실, 종료 대기 0 조건을 모두 통과했다.

## 원인과 수정

기준은 `6591bca`이며, 첫 `baseline`에는 종료 시 이미지별 진행 기록만 추가했다.
원시 증거는 `.build/kmon-images-20261023/`에 보관한다. Windows 11 28000,
2 논리 CPU, 약 4 GiB RAM의 같은 시험 호스트에서 순차 실행했다.

- 캐시 368개 중 같은 프로세스 생성 시각·이미지 기준 주소에 해당하는 경로 별칭이
  90개였다. 고유 이미지 278개 중 65개만 한 번 이상 순회했고, 각 대조군의
  KERNELBASE와 ntdll은 중간에서 멈췄다. DOS 경로와 장치 경로의 별도 커서가
  같은 앞부분을 반복 비교했다.
- 참조 확인만으로 생성된 이미지 작업 58개가 전체 순회를 시작하지 못했다.
  큰 종합 검사 사이에 전체 이미지 작업을 별도로 이어가는 스케줄링이 없었다.
- 완료 직후 작은 이미지를 다시 처음부터 검사했다. 현재 순회의 남은 페이지 수만
  보고 과거 완료 수나 실제 바이트 검증률을 알 수 없었다.
- 카탈로그가 커지면 매 관측·조회마다 전체 최대 16,384개 기록을 훑고, 퇴출 때도
  전체 최소 시각을 찾았다. 순회 범위를 넓힐수록 이 비용이 다른 검사를 지연시켰다.

같은 프로세스 인스턴스·기준 주소에서 원본 메타데이터와 양쪽 파일 핸들의
전체 파일 ID·볼륨 ID를 확인한 경우에만 커서를 공유한다. 문자열 정규화나
파일 이름으로 합치지 않는다. 다른 파일·재사용 PID는 별도 작업으로 유지한다.

분석 스레드의 기존 검사 경계에서 최대 64페이지를 이어서 비교한다. 비교 단계의
페이지 사이 시간 예산은 25ms이며, 추가 순회 간격은 최소 50ms다. 결과 게시 비용도
페이지 상한으로 제한한다. 감시 작업과 배경·커널 작업은 3:1 배정한다. 그룹 안에서는
프로세스 생성 세대별로 순환한 뒤 가장 오래 기다린 이미지를 선택한다. DLL이 많은
프로세스가 작은 프로세스의 검사 차례를 빼앗지 않도록 했다.
레이아웃·참조 대기가 256개 이상이면 추가 순회를 양보한다. 완료된 순회는 30초,
식별 실패는 5초 뒤 재시도한다. 기존 PE/PDB·재배치·안정된 바이트의 재검증을 유지한다.
프로세스 안에서 첫 순회와 재검사가 경쟁하면 3:1로 배정한다. 이미 끝난 작은
이미지를 다시 도는 동안 큰 이미지의 첫 꼬리 검사가 밀리지 않게 하고, 재검사도
굶기지 않는다. 백그라운드 재개로 캐시 발견 시각을 갱신하지 않아 종료된 프로세스의
실패 작업이 영구히 새 항목처럼 남지 않게 했다.

`coverage.image_progress`는 종료 시 현재 커서와 마지막 완료 순회의 바이트 합계를
남긴다. `image_traversed_items`는 한 번 이상 순회한 캐시 항목 수이며, 깨끗한 이미지
수 또는 현재 시점의 원자적 스냅샷을 뜻하지 않는다.

카탈로그는 부팅 ID·PID·생성 시각별 기록 색인과 `(마지막 관측 시각, 세대)` 순서의
퇴출 색인을 유지한다. 커널의 생성 시각 예외와 EPROCESS·세션의 선택적 일치 조건은
기존과 같다. 인덱스 안에서도 동일한 정체성·겹침·오래된 관측 검사를 적용한다.
이전 구현과 20,000개 혼합 연산의 세대·기록·참조 연결·퇴출 결과를 ASan 하에서
대조해 일치했다. 같은 계측 실행의 18,000개 관측/32개 프로세스 벤치마크는
14,484ms에서 4,187ms로 줄었다. 이는 카탈로그 합성 측정이며 전체 KMON 배수로
해석하지 않는다. 증거는 `catalog-differential.cpp`, `.log`에 있다.

## 실험과 중간 회귀

`baseline-tail`부터 동일한 7개 대조군을 각각 180초 관찰한다. 기존 6개에
`overwrite-tail`을 추가했다. 모든 테스트 실행 파일에는 실행하지 않는 1 MiB
`.kntail` 섹션이 있고, 새 양성 대조군만 마지막 페이지의 16바이트를 수정한다.
출력한 RVA가 포함된 페이지의 `finding.code_modified`를 요구한다. 정상 대조군은
그 섹션을 수정하지 않는다.

고정 비교 집합은 대조군 7개 각각의 실행 파일·KERNEL32·KERNELBASE·ntdll, 총 28개다.
발견된 캐시 개수가 달라지는 전체 호스트 비율보다 이 고정 집합을 우선한다.
`-RequireImageCompletion`은 28개 모두 순회하고 읽기 오류가 없으며,
실행 파일 자체는 모든 바이트를 비교했는지 검사한다. 시스템 DLL의 로더 변경 가능
바이트는 제외량과 partial 상태를 유지한다.

이전 코드의 `baseline-tail`은 28개 중 7개만 순회했으며 꼬리 변조를 탐지하지 못했다.
기존 양성 대조군 4개는 탐지했다. 이벤트·큐 손실과 종료 대기는 모두 0이었다.
최초 계측 실행의 정상 `hold`에서는 초기 로더 동작의 레이아웃 변경 관찰 4건이
기존 검증기의 `finding.*` 접두사 검사에 걸렸다. 제품이 이미 `observation`으로
분류한 `finding.layout_change`만 별도 집계하도록 검증기를 수정했다. 다른 탐지 조건은
유지하고 원시 변경 관찰도 모두 보관한다.

중간 `candidate-a`는 256페이지 배치로 28개 순회와 꼬리 탐지를 회복했지만,
기존 대조군 두 개의 검사 기회를 지연시키고 종료 레이아웃 작업 41개를 남겼다.
최종 결과에서 제외한다. 이후 `final-a`라는 이름의 중간 실험도 32페이지 배치만으로는
공정성을 회복하지 못했으며 종료 대기 32개가 남아 실패했다. 자식 콘솔 호스트까지
포함한 감시 프로세스가 14개였고, DLL이 많은 호스트가 이미지별 차례를 점유했다.
최종 코드는 프로세스별 공정 배분·64페이지 상한·큐 양보를 함께 적용했다.
레이아웃/참조 종료 예산은 실제 5초 제한에 걸린 증거에 따라 10초로 늘렸다.
정체성·매핑·오래된 관측 거부 검사는 유지한다.

카탈로그 색인을 추가하기 전의 `final-b`(180초)는 24/28개 순회와 고유 페이지
8,132개를 비교했으며 모든 대조군의 기대 탐지·종료 대기 0을 확인했다. 그러나
전체 순회 조건에는 미달했고, 240초 `final-c`도 미달했다. 시간만 늘리는 것으로
회귀가 해결되지 않아 카탈로그 조회 비용까지 수정했다. 이 중간 실행들도 최종
통과 실행과 구분한다.
색인 적용 후 `final-e`도 8,300페이지까지 확대했지만 완료 이미지의 재검사 때문에
네 ntdll 꼬리가 남았다. 최종 코드에서는 첫 순회/재검사 3:1 배분으로 보완했다.

검증기는 모든 JSONL을 파싱하되 페이지 주소는 집합으로 집계한다. 확대된 검사에서
반복 페이지 이벤트 전체를 PowerShell 객체로 보관하느라 메모리를 소모하지 않는다.
모든 캡처 청크의 크기·SHA-256, 요청별 바이트 합계, case/layout 내보내기,
서비스 정리·정상 종료·같은 부팅 상태도 검사한다.

최종 각 실행의 완료 순회 비교 바이트는 34,843,508이고, 읽기 실패는 0,

머리 2페이지와 꼬리 1페이지에 해당했고, 다른 프로세스의 코드 변조 finding은 없었다.

모든 탐지가 관찰 시간 안에 있었지만 지연이 일률적으로 개선됐다고 주장하지 않는다.
종료 시 원본·레이아웃·참조·캡처 대기는 모두 0이며, 미분석 종료 이벤트도 0이다.
매핑·정체성·관측 시각 검사에서 거부한 레이아웃 후보는 F/G 각각 15/0개로 별도 유지한다.
최종 바이너리 SHA-256은 두 실행 모두
`34A0DA4703356C7EB19A0F7A78D3B0A9D6A4E6D842B2359D974529827D30968C`다.
기준과 최종의 테스트 바이너리 SHA-256은
`62C7DADBED21C1B96C344D8D3BB7C177148AED117574EF2C331C8A909839F050`로 같다.

Release 빌드, 전체 자체 검사(timeline 28, MCP 89, console 557, commands 2,961,
remote 66 및 connect 인수 검사), 핵심 엔진 ASan 7개 묶음과 hunting 11,326,
pages 54, FP 49개를 통과했다. 20,000개 카탈로그 대조 연산도 ASan에서 통과했다.
전체 모니터 바이너리를 ASan으로 실행했다는 뜻은 아니다. 커서 재개 후 꼬리 변조,
완료 이력 보존, 파일 별칭/다른 파일/PID 재사용, 프로세스별 공정 배분과 첫 순회/재검사
비율, 카탈로그 갱신·퇴출·커널 정체성 예외를 회귀 검사에 추가했다.

`comparison-final.json`, 두 `validation.json`, `image-summary.json`에 집계가 있고,
`cleanup-final.json`에서 서비스·테스트 프로세스 0과 같은 부팅 상태를 확인했다.

## 남는 partial

고정 집합의 제외 140바이트는 프로세스마다 KERNEL32 4바이트, KERNELBASE 4바이트,
ntdll 12바이트다. 원본 PE의 동적 재배치표와 실제 제외 주소를 대조했다.
각 RVA는 `0x87011`, `0x1A8011`, `0x173011/0x173021/0x173031`이며 각각 4바이트다.
이 바이트를 검증했다고 표시하지 않아 시스템 DLL 21개의 바이트 검증 상태는 여전히
partial이다. 테스트 EXE 7개는 전체 바이트를 비교했다. 메타데이터 진단과 대조 증거는
`image-exclusions.log`, `check-exclusions.py`에 있다.

전체 호스트의 모든 이미지가 완료된 것은 아니다. 큰 브라우저 이미지, 배경 작업,
재검사 중인 이미지가 남아 F/G의 현재 순회 `image_remaining_pages`는
245,878/106,443이다. 발견된 캐시 집합과 재검사 상태가 달라지는 수치이므로
이 감소율을 성능 지표로 사용하지 않는다. 삭제된 SEC_IMAGE의 원본 파일도 읽을 수 없다.
별도 캡처 경로의 probe 읽기 오류 12,288바이트는 두 번 모두 남았으며, 확인된 접근 불가
범위 212,992/405,504바이트도 제외로 보관했다. 위의 이미지 비교 읽기 오류 0과 구분한다.
결과는 이 대조군과 관찰 구간의 증거이며 다른 워크로드 전체의 무누락·무오탐 보장은 아니다.

## 근거와 재현

파일 별칭의 정체성 기준은 Microsoft의 [FILE_ID_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_id_info),
실행 섹션·폐기 가능 구간과 재배치의 해석은 [PE 형식](https://learn.microsoft.com/en-us/windows/win32/debug/pe-format)을 참고했다.
분석 가능한 실제 메모리 바이트만 비교하며, 읽을 수 없는 범위를 원본 파일로 채우지 않는다.

```powershell
.\tools\build.ps1 -Configuration Release
.\x64\Release\KnLiveDbg.exe --self-test all
.\tools\validate-kmon-core.ps1 -Sanitize
.\tools\validate-kmon-live.ps1 -ObserveSeconds 180 -ProbeDriver `
  -RequireQueueHealth -RequireCompletedWork -ImageSweepFixtures -RequireImageCompletion
```
