# KMON 배경 이미지 완료와 이름 조회 재검증

## 범위와 기준

기준은 `46d5c9b`다. 설치된 실제 x86 VCTIP, 같은 양성 9개·음성 4개 대조군,
콘솔 자식까지 27개 감시 PID를 유지하며 전체 프로세스 모드로 600초 실행한다.
실행 중에는 빌드와 대규모 로그 분석을 하지 않는다. 전후 실제 System.Data.dll
주·보조 뷰를 별도 프로그램으로 읽어 독립 비교한다.

원본 증거는 `.build/kmon-background-names-20261024`에 보존한다. 실행 파일을
별도 이름으로 고정하고 전후 해시를 확인한다. 하네스 종료, 전후 스냅샷,
`runner.done`을 모두 확인한 뒤 다음 빌드나 실행을 시작한다.

## 수정 이유

배경 최초 순회는 일반 회전에 1/3, 대형 이미지에 2/3를 배정했다. 대형 작업은
마지막 검사 시각 순으로 고르므로 바이트를 넓게 비교하는 데 유리하지만 남은
페이지가 적은 이미지에도 다음 회전까지 같은 대기를 부과했다.
새 기준 실행의 종료 시점에도 배경 최초 미완료 이미지 1,470개 중 408개는
64페이지 이하만 남았다. `hgfs.dll`, `wosc.dll`, `wdi.dll` 등은 1페이지만 남은
상태에서 후속 순회 선택 횟수가 0이었다. 이는 레이아웃 후보 경로에서 일부를
비교한 뒤 전용 후속 순회를 받지 못한 상태다. `baseline/tail-analysis.json`에
종료 시점의 캐시 진단을 보존했다.

감시/배경 및 최초/재검사 그룹 배분은 유지한다. 배경 최초 순회의 세 차례를
일반 회전, 대형 이미지, 1,024페이지 이하 잔여 작업 순으로 사용한다. 마지막
차례에서는 남은 페이지가 적은 작업을 먼저 고르고, 해당 작업이 없으면 대형
이미지에 돌려준다. 대형 이미지의 별도 차례, 일반 프로세스 회전, 주기 재검사를
유지한다. 짧은 작업이 계속 생겨도 이 세 차례 전체를 차지할 수 없다.
25ms 검사 예산, 1,024페이지 상한, 메모리/파일 동일성 검사와 완료 조건은 바꾸지 않는다.
`image_completion_priority_turns`와 이미지별 `completion_priority_turns`는 선택 횟수이며
바이트 비교 성공이나 완료를 뜻하지 않는다.

이름 조회는 할당마다 첫 committed 영역에서 한 번 시도했다. 실패해도
`ImageNameAttempts`에 남아 그 순회가 끝날 때까지 다시 시도하지 않았다. 이전 실행의
오류 59는 [Windows 오류 코드 문서](https://learn.microsoft.com/en-us/windows/win32/debug/system-error-codes--0-499-)의
`ERROR_UNEXP_NET_ERR`에 해당한다. 당시 로그에 실패 주소가 없어 실제 네트워크 문제나
매핑 해제를 원인으로 확정할 수 없다. [GetMappedFileNameW 문서](https://learn.microsoft.com/en-us/windows/win32/api/psapi/nf-psapi-getmappedfilenamew)의
실패 반환만으로 특정 운영체제 내부 원인을 추정하지 않는다.

수정본은 이름 조회 실패 시 관측했던 영역과 현재 매핑이 일치하면 한 번만 다시
조회한다. 재조회 전후에도 할당·영역·상태·보호 속성이 맞아야 이름을 채택한다.
접근 거부·잘못된 핸들/인자·버퍼 부족은 반복하지 않는다. 이름을 얻지 못하거나
매핑이 바뀌면 원래 실패를 유지한다. 이전 순회의 이름을 복사하지 않는다.
이는 비원자적 관측이며 관측 사이에 완전히 같은 속성으로 재사용된 매핑까지 증명하지 않는다.
후속 검사도 기존 프로세스 세대와 실제 이름 확인을 계속 수행한다.

스냅샷 및 `coverage.layout`에 다음 정보를 추가했다.

- `image_name_retry_attempts`, `image_name_recovered`: 실제 재조회와 조건을 만족한 회복 횟수.
- `image_name_diagnostics`: 실패 주소, 할당 주소, 최초/재조회 오류, 단계, 재조회 시 매핑.
- `image_name_diagnostics_omitted`: 스냅샷당 32개 진단 상한으로 생략한 수.

기존 이름 실패/오류 합계는 해소되지 않은 공백을 계속 나타낸다. 회복한 최초 오류는
진단에 남는다. 상세 진단과 생략 수의 합계도 독립 대조한다.
회복 수는 이름 재조회 절차의 성공이며, 이후 저장 용량이 부족하면 해당 이름은
별도 용량 공백으로 남는다. 기존 조회 함수의 버퍼 확장은 이 재시도 횟수와 구분한다.

## 검증 방법

네이티브 self-test에 오류 59 후 회복, 반복 실패, 재조회 전후 매핑 변경, 다른 할당,
접근 거부 및 진단 상한 반례를 추가했다. 이 테스트는 API 경계에서 오류를 주입하며
과거 운영체제 오류의 실제 원인을 재현한 것으로 취급하지 않는다.
스케줄러는 짧은 작업이 계속 남는 조건에서 일반 회전·대형 작업·재검사의 차례를
검증하고, 짧은 작업이 없을 때 차례가 반환되는지도 확인한다.

`tools/validate-kmon-layout-names.py`는 모든 레이아웃 이벤트와 최종 스냅샷의
이름/할당/공백 회계 및 회복 진단을 검증한다. `--allow-legacy`는 비교 기준의
진단 없는 형식을 읽기 위한 옵션이며 수정본에는 사용하지 않는다.
`tools/test-kmon-layout-names.py`의 8개 반례는 잘못된 회복·누락된 증거·허위 재시도를 거절한다.

```powershell
tools/build.ps1 -Configuration Release
x64/Release/KnLiveDbg.exe --self-test all
python tools/test-kmon-layout-names.py
tools/validate-kmon-live.ps1 -AllProcessLayouts -ImageSweepFixtures -SecondaryViewFixtures `
    -ObservedProcessId $actualVctipPid -ObserveSeconds 600 -ProbeDriver `
    -RequireQueueHealth -RequireCompletedWork -RequireImageCompletion `
    -RequireLayoutNameAccounting -RequireFreshLayouts `
    -MonitorExecutablePath $frozenMonitor -OutputDirectory $run
python tools/validate-kmon-layout-names.py $run
python tools/validate-kmon-capture-accounting.py $run `
    --require-discardable --require-kernel-quantum --require-root-layout-cache
python tools/validate-kmon-vctip.py audit --run $run --before $beforeSnapshot --after $afterSnapshot
```

배경 비교는 양쪽 실행에서 식별된 부팅·PID·생성 시각의 교집합을 사용하며,
비교 바이트가 없는 프로세스도 포함한다. 주소 구간을 합쳐 중복 비교를 제거하고
완료 이미지 수와 함께 비교한다. 기준에서만 검사한 범위도 공개하며 전체 호스트의
누락 0이나 모든 실행 간 범위 포함을 주장하지 않는다.

## 실행 결과

`candidate-a`와 `candidate-b`는 KMON 시작 전에 실제 VCTIP 두 뷰 준비가 실패한
시도이며 최종 반복 검증에서 제외한다. 이번 빌드 중 생성된 `Hostx86/x64/VCTIP.EXE`
PID 14212가 두 뷰를 보유했고, 새 `Hostx86/x86/VCTIP.EXE`에는 뷰가 없었다.
빌드 로그 시간 범위·정확한 경로·생성 시각으로 소유한 보조 프로세스를 확인해
정리했다. 이후 시작은 고정 시간 대기 대신 두 뷰가 준비됐는지 확인한다.
원래 기준 실행과 같은 x86 VCTIP 바이너리를 사용한다.

Release 빌드와 `--self-test all`이 성공했고, 이름 회계 Python 테스트 8개가 통과했다.
네이티브 self-test의 최초 실행은 PowerShell 5가 테스트에서 의도한 stderr를
종료 오류로 취급해 중단됐다. 래퍼에서 네이티브 종료 코드를 확인하도록 고친 뒤
같은 바이너리로 전체 테스트를 다시 끝냈다. 유효한 결과는 `selftest-a.log`와
종료 코드 0인 `selftest-a.exit`다. 코드 변경 7개 파일의 해시도 빌드 때 저장한
`candidate-a.source-hashes.json`과 최종 확인에서 일치했다.

이름 감사는 기준 18,722개, 수정본 18,043개·18,744개의 `coverage.layout` 이벤트와

구분했다. 조회 실패·잘림·조회 불가·용량 실패는 모두 0이었다. 자연 발생 오류 59는
이번 기준 및 반복 실행에서 관측하지 못했다. 따라서 실제 환경의 회복률이 높아졌다는
주장은 하지 않으며, 실패 주소를 보존하고 안전하게 한 번 재조회하는 동작은 API 경계의
오류 주입과 매핑 변경 반례로 검증했다.

실제 VCTIP PID는 기준 10276, 수정본 624·12376이었다. 각 실행의 System.Data.dll
주·보조 뷰 모두 뷰당 3,414,016바이트를 비교했고 실패·제외·코드 차이가 없었다.
전후 독립 메모리 스냅샷과 재배치 재구성도 일치했다.

보호된 프로세스 및 실행 시간 안에 선택되지 않은 작업의 공백은 남는다.

| 위 요청의 페이지 수집 간격 p95 / 최대 (ms) | 1 / 203 | 2 / 281 | 1 / 54 |

캡처 합계는 요청에 속한 바이트이며 별도 이벤트 캡처는 감사 결과의
`standalone_bytes`로 구분한다. 제외한 바이트를 검사 성공으로 세지 않는다.
`--require-discardable --require-kernel-quantum --require-root-layout-cache`를 적용한
감사에서 요청별 저장·실패·제외·미방문 회계가 모두 일치했다.

대조군 밖 CLR·User32·ntdll 코드 차이는 저장한 메모리와 독립적인 예상 바이트 재구성에서
실제 차이로 확인했다. Node 및 skia의 PE 필드 차이도 독립 대조와 일치했다.
이들은 악성 여부가 확정된 탐지가 아니다. 누락·오탐 0은 알려진 13개 대조군과
실제 System.Data.dll 두 뷰 검증에 한정한다.

개선한 스케줄러와 이름 재조회 경로는 위 기능 검증을 통과했다. 전체 호스트의
완전 검사, 모든 실행 간 범위 포함, 자연 발생 이름 오류의 회복률은 보장하지 않는다.
세부 수치는 각 실행의 `image-coverage.json`, `layout-name-audit.json`,
`capture-accounting.json`과 `final-b/coverage-comparison.json` 및 독립 감사 로그에 보존했다.
