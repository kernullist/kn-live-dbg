# KMON 커널 캡처와 레이아웃 단서의 검사 지연 검증

## 대상과 판정 기준

기준 커밋은 `819125b`다. 실제 x86 VCTIP와 13개 대조군을 동시에 유지하고,
전체 프로세스 레이아웃 수집을 600초 실행한다. 대조군의 콘솔 자식까지 포함해
27개 PID가 감시되며, 실제 VCTIP는 설치된 Visual Studio 실행 파일을 직접 실행한다.
빌드와 전체 로그 분석은 네이티브 수집이 끝난 뒤 수행한다.

원본은 `.build/kmon-capture-latency-20261024`에 보존한다. 검증은 큐 건강도,
종료 시 미처리 작업, 이미지 완료, 이름 수집 회계, 후보 유효기간을 모두 요구한다.
실제 System.Data.dll 두 뷰의 전후 스냅샷과 전체 실행 범위를 독립적으로 비교한다.
추가 코드 차이와 PE 식별자 관측도 저장한 바이트와 디스크를 대조한다.

## 원인과 수정

공통 `driver_image` 읽기 실패 12,288바이트는 Probe 이미지의 RVA `0x7000`,
`0x8000`, `0x9000`에 해당한다. 이 페이지는 각각 `INIT`, `.rsrc`, `.reloc`이며
PE의 폐기 가능 플래그를 가진다. Microsoft의 [PE 형식 문서](https://learn.microsoft.com/en-us/windows/win32/debug/pe-format)는
이 플래그를 폐기 가능한 섹션으로 정의한다. 플래그만으로 실제 폐기를 확정하지 않는다.
수정본은 먼저 읽기를 시도하고, 주소 변환도 불가능하며, 캡처한 라이브 헤더가
재확인된 경우에만 `unreadable_discardable_section`으로 원인을 구분한다.
겹친 섹션, 잘린 헤더, 크기 불일치, 일반 섹션에는 적용하지 않는다.
해당 바이트는 `skipped`와 `discardable_unreadable_bytes`에 계속 남고,
요청 크기나 완료 판정에서 제거하지 않는다. 이 분류 변경은 검사 범위 증가가 아니다.

주소 공간 루트를 통한 캡처는 내부 읽기 함수가 이미 물리 읽기 전후의 페이지 테이블
동일성을 검사하는데 바깥에서 주소 변환을 두 번 더 했다. 내부 검사의 결과를 반환해
중복 호출을 없앴다. PFN뿐 아니라 페이지 크기·상위 엔트리·권한 검사는 유지한다.
프로세스 생성 시각과 루트의 동일성도 읽기 전후 확인한다.
프로세스 루트 확인에 필요한 EPROCESS 필드 배치는 캡처 작업자 실행 중 한 번만
PDB에서 구한다. 이전에는 페이지마다 읽기 전후로 필드 전체를 반복 조회하여
공유 DbgHelp 잠금과 캡처 대기를 늘렸다. 캐시는 현재 심볼 바인딩과 작업자 수명에
한정되며, EPROCESS·PID·생성 시각·CR3나 메모리 바이트는 캐시하지 않는다.
각 읽기 전후의 실제 루트 확인과 페이지 테이블 검사는 유지한다.
`capture_root_layout_resolutions`와 `capture_root_identity_checks`를 각각 기록한다.
조각의 `request_age_at_read_start_ms`와 `page_read_duration_ms`로 요청 접수 이후
읽기 시작까지의 경과 시간과 실제 읽기 경로의 소요 시간을 구분한다. 전자는 후속
페이지의 경우 앞선 페이지를 처리한 시간도 포함한다.
추가 실측에서 16KB 커널 창의 첫 페이지와 후속 페이지 사이에 수초의 대기가 있었고,
후속 읽기는 물리 읽기 전에 주소 변환부터 실패했다. 한 번의 지연 재시도를 넣은
중간 버전은 91페이지를 재시도했지만 회복한 바이트가 0이었다. 이 재시도는 제거했다.
커널 캡처는 이제 최대 4페이지의 연속 읽기 차례를 사용한다. 중간 버전의 25ms 시간
제한은 한 페이지 처리에 127ms가 걸린 실행에서 16KB 창을 다시 나눠 약 3.5초의
대기를 만들었다. 이 시간 제한 대신 페이지 수로 차례를 제한한다. 각 페이지의 동일성
검사와 공백 회계는 그대로 유지하며, 큰 요청은 제한에 도달하면 다시 큐에 넣어
다른 요청에 차례를 준다. 읽기 완료 대기 시간과 연속 처리한 추가 페이지 수도 기록한다.
연속 처리 수는 성공적으로 읽은 바이트 수가 아니다. 종료 유예를 늘리지 않는다.
변환 전/후, 물리 읽기, 매핑 변경 중 실패한 단계와 원래 오류를 로그에 남긴다.
Microsoft의 [MmCopyMemory 문서](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntddk/nf-ntddk-mmcopymemory)는
수명이 통제되지 않는 메모리의 읽기가 실패할 수 있음을 명시한다. 실패 페이지를
성공으로 간주하거나 위험한 MDL 읽기를 활성화하지 않는다.

이번 부하에서 정밀 사용자 검사에는 한 번에 감시 대상 4개, 다른 우선 대상 최대
2개, 배경 대상 2개가 배정된다. 레이아웃에서 이미 실행 가능한 private/mapped 영역이나 읽거나
해석할 수 없는 이미지 참조를 발견해도 이 정보가 검사 순서에 반영되지 않았다.
공용 이미지 조회 함수는 참조 읽기 실패와 캐시 접수 보류·재검사 대기를 모두 null로
반환했다. 실제 참조 읽기/해석 실패를 별도 출력으로 구분하여, 자원 보류를 오류로
오인하지 않고 우선 요청에 연결한다. 이제 감시 몫 중 최대 2개를 해당 단서에 배정한다. 나머지 감시·우선·배경 회전은
유지하고, 비어 있는 몫 때문에 정밀 검사량을 늘리지는 않는다. 중간 버전에서 빈 몫에
감시 대상을 더 넣었을 때 공통 배경 프로세스의 비교 범위가 약 15% 줄어 이 변경은
제거했다. 프로세스 생성 시각을 키에 포함하고,
이미 검사한 세대의 변하지 않은 영역은 주기적으로 재발견되어도 우선 요청을 만들지
않는다. 실제 레이아웃 변경은 30초 냉각 중에도 보관하고, 직전 정밀 검사를 시작한 지
30초가 지나면 우선 선택할 수 있다. 대기 요청은 4,096개로 제한하고 중복 요청은 최초
대기 시각을 바꾸지 않는다. 일반 순서에서 먼저 검사해도 대기 요청을 해소한다.
새 탐지 판정이나 이름 예외는 추가하지 않는다.

우선 검사 도입 후 공통 배경 프로세스의 비교 범위가 줄어든 실행도 확인했다.
재실행한 기준과의 차이도 약 11%였으므로 단순한 호스트 변동으로 처리하지 않았다.
정밀 사용자 검사는 모듈마다 보류 작업을 처리하지만, 모듈이 적은 private/mapped
메모리 검사에는 같은 기회가 부족했다. VAD 조회 이후와 메모리·VAD·PTE 레코드 사이에서
50ms가 지난 경우 보류 분석을 처리한다. 실제 호출 완료 후 다음 시각을 잡아 연속
호출을 제한하고, 잠금이나 이미지 캐시 참조를 보유한 구간에서는 호출하지 않는다.
프로세스 세대와 메모리 검증은 유지하며 대상 수·이미지 그룹별 몫은 바꾸지 않는다.
실제 양보 횟수는 `user_memory_analysis_yields`로 기록한다.
50ms는 레코드 경계에서 확인하는 기준이며, 단일 장치 호출을 중단하거나 최대 대기
시간을 보장하지 않는다.

## 검증 도구

`tools/validate-kmon-capture-accounting.py`는 실제 캡처 조각의 길이와 SHA-256,
읽기·실패·제외·미방문 합계를 독립 대조한다. 중간 버전에 재시도 기록이 있으면
그 횟수와 회복 바이트도 대조한다. 16KB 커널 캡처의 페이지 간 대기 분포를 집계한다.
폐기 가능 공백은 저장된 헤더를 별도로 해석해 해당 섹션과 대조한다.
`--require-discardable`은 이 경로가 실제로 실행됐을 것을 요구한다.
`--require-kernel-quantum`은 커널 연속 읽기 차례가 실제 실행됐을 것을 요구한다.
`--require-root-layout-cache`는 한 번의 필드 배치 조회와 반복된 실제 루트 확인을 요구한다.
`tools/test-kmon-capture-accounting.py`는 조작된 완료량, 누락·중복 조각,
잘린 헤더, 잘못된 섹션·플래그·저장 바이트, 허위 재시도 회복을 거절한다.
읽기 요청과 직접 저장된 참조 조각은 구분하며, 직접 저장 조각도 길이와 해시를 검증한다.
최종 파이프라인 합계와 요청별 합계가 일치해야 한다. 반례 검사는 총 15개다.

개발 중 `candidate-a`는 네이티브 종료 후 바이너리 해시 확인과 다음 빌드가 겹쳐
증거 게이트가 실패했다. 이 실행은 최종 통과 근거에서 제외한다. 이후 실행 파일을
별도 이름으로 복사해 고정하고, 래퍼의 `runner.done`과 전후 스냅샷까지 완료된 뒤
다음 작업을 진행한다. `final-a`라는 중간 디렉터리의 바이너리는 null 반환의 의미를
구분하기 전 버전이므로 최종 반복 검증과 구별한다. `verified-a`는 지연 재시도,
`quantum-a`는 25ms 제한이 남은 중간 버전이다. `bounded-a`는 반복 PDB 조회를
제거하기 전 버전이며 초기 캡처 대기와 읽기 실패 증가가 관측돼 최종 근거에서 제외한다.
`cached-a`는 캡처·대조군·종료 검증을 통과했지만 배경 범위 감소가 남은 중간 버전이다.

## 반복 실행 방법

Release 빌드와 `KnLiveDbg.exe --self-test all`을 완료하고 실행 파일을 별도 이름으로
고정한다. 설치된 `Hostx86\x86\VCTIP.EXE`를 직접 실행해 PID와 생성 시각을 기록한다.
실제 VCTIP에 대해 실행 전후 `validate-kmon-vctip.py snapshot`을 수행하며,
네이티브 검증은 다음 조건을 사용한다.

```powershell
& .\tools\validate-kmon-live.ps1 -AllProcessLayouts `
    -ImageSweepFixtures -SecondaryViewFixtures -ProbeDriver `
    -ObservedProcessId $actualVctipPid -ObserveSeconds 600 `
    -RequireQueueHealth -RequireCompletedWork -RequireImageCompletion `
    -RequireLayoutNameAccounting -RequireFreshLayouts `
    -MonitorExecutablePath $frozenMonitor -OutputDirectory $runDirectory
python .\tools\validate-kmon-vctip.py audit --run $runDirectory `
    --before $beforeSnapshot --after $afterSnapshot
python .\tools\validate-kmon-capture-accounting.py $runDirectory `
    --require-discardable --require-kernel-quantum --require-root-layout-cache
python .\tools\test-kmon-capture-accounting.py
```

양성 대조군은 overwrite, overwrite-tail, orphan-mapped-rx, orphan-private,
orphan-image와 PE32/PE32+의 code·reloc 단일 바이트 변경 4개다.
음성 대조군은 hold, mapped-readonly, alias32-clean, alias64-clean이다.
실행 사이에는 래퍼 종료와 전후 스냅샷을 모두 기다리고, 직접 시작한 VCTIP만
경로·PID·생성 시각을 재확인한 후 정리한다.

## 최종 반복 실행 결과

최종 Release 빌드(`build-i`)와 `--self-test all`은 종료 코드 0이다. 캡처 회계의
15개 반례 검사도 통과했다. 같은 실행 파일로 `fair-a`, `fair-b`를 각각 600초
실행했으며 두 실행의 네이티브 게이트와 VCTIP·배경 코드·PE 식별자·보조 이미지·
캡처 회계·범위 집계가 모두 통과했다. 커밋 전 8개 변경 C++/헤더 파일의 해시를
빌드 직후 기록과 대조했으며 모두 일치했다.

읽기 실패 감소 중 12,288바이트는 공백 분류를 바로잡은 것이고, 나머지
126,976바이트의 `orphan_wx` 실패가 최종 반복에서 발생하지 않은 것이 실제 캡처
개선이다. 원본 `baseline`에서도 이 실패가 90,112바이트였다. 16KiB 지연 차이는
첫 읽기를 기다린 시간이나 전체 요청 지연이 아니라 같은 요청의 페이지 사이에서
벌어진 시간이다. 서로 다른 실행의 커널 창은 동일한 주소 집합을 뜻하지 않는다.

Probe 드라이버는 두 최종 실행 모두 40,960바이트 중 28,672바이트를 저장하고
12,288바이트는 여전히 검증하지 못했다. `partial`을 유지한다. 사용자 페이지의
보호·미커밋 구간도 제외 합계에 남는다. 따라서 실패 0을 전체 메모리의 공백 0으로
해석해서는 안 된다. 제외 바이트 전체가 기준보다 늘어난 사실도 표에 함께 기록했다.

최종 A/B의 루트 필드 배치 조회는 각각 1회, 실제 프로세스 동일성 확인은
3,268/3,574회였다. 커널 연속 처리 추가 페이지는 959/1,046개,
사용자 메모리 순회 중 보류 분석 처리는 215/252회였다.

## 대조군 탐지 지연과 독립 검증

아래는 기존 하네스의 `first_detection_seconds`, 즉 각 대조군의 `started_utc`부터

음성의 예상 밖 탐지는 없었다. 대조군 이미지 완료 기록은 각 최종 실행 58개다.

실제 VCTIP는 A에서 PID 5192, B에서 PID 4028이었다. 각 실행의 System.Data.dll
주·보조 뷰는 모두 3,414,016바이트씩 비교 완료했고 실패·제외·코드 변경 탐지는 0이다.
독립적인 실행 전후 메모리 스냅샷에서도 정규화한 실행 범위의 차이는 0이었다.
실행 종료 후 직접 시작한 VCTIP만 경로와 생성 시각을 확인해 정리했다.

추가 관측된 `clr.dll` 229바이트와 `user32.dll` 16바이트 차이, B의 다른 배경
프로세스에서 관측된 `ntdll.dll` 차이는 저장한 바이트와 독립 재배치 복원 결과가
일치했다. Node/skia의 PE 식별자 불일치도 저장된 헤더와 디스크로 확인했다.
이는 실제 차이의 관측이며 악성 여부를 확정하지 않는다. 이번 무누락·무오탐 판단은
정답을 아는 13개 대조군과 실제 System.Data 뷰에 한정한다.

## 배경 범위와 남은 공백

`baseline-recheck`와 각 최종 실행에 공통으로 등장한 PID·생성 시각이 확인된
배경 프로세스 194세대를 비교했다. 비교 바이트가 없는 세대도 포함했으며
0바이트 세대는 각 쌍의 양쪽 모두 8개다. 주소 구간의 합집합으로 반복 비교를 제거한다.

고유 비교 바이트는 늘었지만 완전히 비교한 배경 이미지 수는 줄었다. 각 실행의
검사 대상·시점이 달라 최종 범위가 기준 범위를 전부 포함하지 않는다. 600초의
제한된 회전 검사로 호스트의 모든 이미지가 완료됐다고 주장하지 않는다.
레이아웃 후보 검사 수도 기준 115,335개에서 A/B 111,091/110,729개였고,
최대 큐 대기는 5,594ms에서 4,954/7,297ms로 변했다. 두 최종 실행 모두
큐 건강도·완료 작업·후보 신선도 게이트는 통과했다.

B의 이름 조회 실패 1건은 배경 `svchost.exe` PID 2256, 생성 시각
`134371975333170003`의 78번째 순회에서 `GetMappedFileNameW`가 반환한 오류 59다.
직전 77회에는 조회 실패가 없었고, 마지막 순회에서는 이미지 할당 55개 중 이름
54개를 얻었으며 변경 구간 64개를 관측했다. 15:49:58 KST의 별도 읽기 전용 조회에서는
같은 세대의 현재 이미지 할당 54개 모두 이름을 얻었다. 원래 실패한 할당 주소를
이 로그로 특정할 수 없어 매핑 해제나 일시적 경합을 확정하지 않는다. 추가 조회는
원래 600초 실행의 공백을 소급해 채우지 않으며 원본 실패 수 1을 유지한다.
상세 근거는 `fair-b/name-gap-followup.json`에 보존했다.

최종 채택 근거는 커널 창의 실제 저장 완료 개선, 지연이 컸던 세 대조군의 반복 개선,
13개 대조군·실제 System.Data 뷰의 검증 통과, 그리고 공백을 보존하는 회계다.
배경 이미지 완료 수와 일부 빠른 대조군 지연의 감소까지 입증한 변경은 아니다.

주요 증거는 각 실행의 `validation.json`, `capture-accounting.json`,
`vctip-validation.json`, `background-code-audit.json`, `identity-audit.json`,
`image-coverage.json`과 `fair-b/coverage-comparison.json`이다. 메모리 원본과 전체
로그는 `.build`에만 보존하고 커밋에는 코드·검증 도구·이 문서를 포함한다.
