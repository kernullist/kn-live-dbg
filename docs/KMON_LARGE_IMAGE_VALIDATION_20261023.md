# KMON 대형 이미지와 동적 재배치 검증 (2026-10-23)

이 문서는 `cefc784` 이후의 대형 배경 이미지 순회와 동적 재배치 제외 구간을 다룬다.
실행 증거는 `.build/kmon-large-images-20261023`에 있다.

## 원인과 변경

기존 스케줄러는 감시 대상 3회마다 배경 작업 1회를 배정하고, 배경 프로세스와
그 안의 DLL을 차례로 선택했다. 65,801페이지 chrome.dll은 이번 기존 버전의
180초 실행에서 22페이지만 비교했다. 페이지 처리 비용만 줄인 중간 버전에서도
차례 부족이 남았다. 이제 추가 검사 선택 8회 중 1회는 아직 첫 순회를 완료하지 못한
4,096페이지 이상 배경 이미지에 배정한다. 감시 작업이 준비되어 있을 때의 3/4 배정, 나머지 배경 차례의
프로세스 순환, 완료 이미지의 재검사는 유지한다. 큰 이미지끼리는 마지막 검사
시각을 기준으로 순환하며 완료한 이미지는 이 우선 배정에서 빠진다.

검사 묶음의 비교 예산은 25ms로 유지하고, 계속 순회의 페이지 상한은 64에서
1,024로 늘렸다. 원본 파일은 묶음 동안
읽기 전용으로 열고 쓰기·삭제 공유를 허용하지 않으며, 시작과 끝에 파일 정체성을
검사한다. 프로세스·매핑·PE/PDB 검증과 변조 바이트의 두 번 읽기는 유지한다.
정상 바이트 복사는 연속 구간으로 처리하고, 완전히 비교된 연속 정상 페이지만
64KiB 경계 안에서 묶어 카탈로그에 기록한다. 변조·실패·제외 페이지는 개별 기록한다.
한 묶음의 예상 상세 등록 수를 64개로 제한해 전체 변조 이미지의 이벤트 폭증도 막는다.
25ms는 비교 루프의 협력적 예산으로, 단일 읽기 호출과 후속 기록까지의 실시간 상한은 아니다.

반복 실행 중 원시 이벤트 분석 큐의 별도 손실도 발견했다. 수집기가 큐 여유와 무관하게
원본 타임라인에서 512건을 읽고 커서를 전진시켜, 분석이 늦어지면 큐 삽입 실패로
이벤트를 버렸다. 이제 큐의 빈자리만큼 읽고 나머지는 원본에 남긴다. 원시 분석 큐가
밀리면 추가 이미지 순회를 잠시 양보한다. 종료 시에는 원본의 마지막 이벤트 ID를
고정하고 그 지점까지 읽어 처리한다. 종료 예산을 넘긴 원본 대기량과 실제 원본
저장소에서 밀려난 이벤트는 각각 미분석/손실로 보고하며 성공으로 숨기지 않는다.

실제 Windows DLL의 제외 5곳은 x64 REL32 함수 재정의였다. KERNEL32/KernelBase의
각 1곳과 ntdll의 2곳은 원본 RVA를 반복하는 레코드였으며 실제로 PE 밖의 주소를
가리켰다. 이 네 곳은 검증 가능한 목적지 목록이 없어 계속 제외한다. ntdll의
`0x173031`은 서로 다른 내부 목적지가 명시되어 있어 4바이트를 검증 대상으로 바꿨다.
파서는 그 목적지 목록을 보존하고, 지원하는 V1 BDD 형태와 AMD64 REL32에 한해
온전한 32비트 목적지가 원본 또는 BDD에서 도달 가능한 파일의 대체 목록에 있는지 확인한다. 단순히 이미지 안에
있다는 이유로 허용하지 않는다. 원본의 분기 값, 실행 섹션, 부호 범위, 다른 가변
범위·재배치와의 중복도 확인한다. 알 수 없는 형식과 경계에 걸친 피연산자는 제외한다.

이 정책은 파일에 정의된 목적지 집합을 검증하며 CPU 기능에 맞는 하나의 목적지를
선택했는지까지 증명하지 않는다. 다른 합법 목적지로 바꾼 경우는 이 정책의 탐지 대상이
아니다. `function_override_compared_bytes`를 기록하고 변조 발견에는 해당 정책도 명시한다. 파일을
신뢰할 수 있는 게시자의 원본으로 인증한다는 주장도 하지 않는다.

## 검사 방법과 결과

확장 대조군은 실제 로더에 등록된, 호출되지 않는 DLL이다. 큰 DLL 두 개는 각각
16MiB 실행 섹션을 가지며 한쪽의 끝 16바이트만 바꾼다. 작은 DLL 두 개는 동일한
DVRT를 가지며 한쪽은 정상 대체 목적지, 다른 쪽은 그보다 1바이트 벗어난 목적지를
사용한다. 대조 DLL의 경로/기능 이름에 대한 생산 코드 예외는 없다.

이 DLL들을 Temp에서 로드하므로 기존 `drop_module` 경로 규칙의 단서가 각 1건씩
발생할 수 있다. 검사 도구는 **정확한 생성 경로**, `event_category=lead`,
`maliciousness=not_established`, 비교 바이트 0을 모두 확인해 별도 집계한다.
코드 변조·고아 매핑 발견은 이 예외에 포함하지 않는다. 정상 분기 대조군을
통과시키기 위해 생산 탐지 규칙을 완화하지 않았다.

최종 모니터 SHA-256은
`B75EB644D920057235421E479E36E9A71A9E485043F181C9B710DEE8AF172294`,
대조 프로그램 SHA-256은
`E87E10E018309B642E88B1BC7B097CF387E6B8911BDF0962C122E5EF06A8A7BE`다.
각 확장 실행은 기존 검증과 같은 감시 이름/PID 범위에서 300초 관찰했다.

이 분석으로 악성/비악성을 새로 판정하거나 생산 탐지 예외를 추가하지 않았다.

기존 시나리오를 동일 최종 바이너리로 240초 재검증한 `standard-final`도 7/7을
통과했다. 기준 이미지 28/28, 고유 페이지 8,519개를 비교하고 일반/끝부분 코드 변조,
mapped RX, private 고아 이미지, SEC_IMAGE 고아 이미지의 양성 5개를 모두 탐지했다.
정상 hold·mapped-readonly의 예상 밖 발견은 0건이었다. 수집/큐 손실, 종료 미분석,
종료 후 테스트 서비스는 모두 0이며 같은 부팅 상태를 유지했다. 캡처 3,580개,
14,642,816바이트를 검증했다. 수집기 최대 간격 828ms, 분석 큐 최고치 1,292건,
종료 처리 시간 2,000ms였다. 대조군 밖의 추가 코드 변경 기록은 없었다.

기준 실행 `stress-baseline`은 기존 `cefc784` 모니터와 확장 대조군을 300초 실행했다.
큰 DLL의 정상/변조 대조군은 각각 2,599/2,713페이지에서 멈췄으며 두 양성 대조군의
`finding.code_modified`가 없었다. 작은 DLL 두 개는 순회했지만 각각 4바이트를
제외해 완전한 바이트 비교가 아니었다. 큐 손실과 종료 대기는 모두 0이었다.
기준 실행의 전체 고유 비교 페이지는 10,188개다. 완료 이벤트가 없는 큰 DLL의
비교량을 0으로 해석하지 않고 최종 진행 이벤트의 실제 비교량을 사용했다.

중간 실행 `stress-e`와 `stress-f`도 확장 대조군 4/4를 통과했다. E의 큰 끝부분
변조/REL32 변조 탐지 시간은 73.69/1.76초, F는 160.26/37.41초다. 처리량이 늘어도
대기 시간은 호스트 부하와 순서에 따라 변하므로 일정한 탐지 지연 개선을 주장하지 않는다.

## 실패한 중간 실행과 남는 범위

`stress-h`는 이미지 20/20 순회와 두 변조 탐지를 통과했지만 원시 이벤트 분석 큐에서
1,200건이 탈락했다. 분석 큐 최고치는 2,048건이었고 TI·레이아웃·캡처 큐 손실은
0이었다. 이 실행은 통과 증거에서 제외하고 위의 수집량 제한과 종료 처리를 추가했다.

`candidate-b`는 PowerShell 검증기의 `[ulong]` 형식 오류로 최종 판정을 하지 못했다.
이 형식을 `[uint64]`로 수정하고 커널 주소의 구간 계산도 따로 확인했다. 이 실행은
통과 증거에 포함하지 않는다.

`stress-d`는 감시 필터를 비워 시작해 전체 프로세스 레이아웃 검사가 활성화됐다.
레이아웃 큐에서 2,773건이 탈락했고 두 미감시 큰 대조군의 검사도 완료하지 못했다.
실패로 보존했으며 이후에는 기존 검증과 동일한 감시 이름/PID 범위로 실행했다.
전체 프로세스 레이아웃 모드의 포화는 이번 변경으로 해결했다고 주장하지 않는다.

실제 배경 브라우저 DLL은 진행량이 늘어도 여전히 partial일 수 있다. 캐시에 새 이미지가
추가되고 완료 이미지의 다음 순회가 시작되므로 전역 `image_remaining_pages`의 증감만으로
개선율을 계산하지 않는다. 같은 PID·생성 시각·이미지 기준 주소의 진행과 비교 바이트를
대조한다. 시험 대상에서의 무누락·무오탐은 호스트 전체 또는 임의의 CPU 구성에 대한
보장이 아니다. 외부 thunk 4곳의 16바이트/프로세스 제외는 유지한다.

이미지 대조군의 읽기 실패는 0이지만 전체 캡처에서는 기존 probe 대조의
실제 읽기 실패 12,288바이트가 별도로 남는다. 알려진 비가독 구간은 I/J에서
각 344,064바이트, 기존 시나리오 재검증에서 278,528바이트다.
캡처 결과의 바이트 합계와 파일 해시 검증이 이를 성공 바이트로 대체하지 않았는지도 확인한다.
한도가 있는 카탈로그 연결 이력의 축출은 별도 수치이며 이벤트 수집 큐 손실과 구분한다.

## 자체 검사와 근거

재현 명령은 저장소 루트에서 실행한다. 실제 드라이버 검증 명령은 관리자 PowerShell을 사용한다.

```powershell
.\tools\build.ps1 -Configuration Release
.\x64\Release\KnLiveDbg.exe --self-test all
.\tools\validate-kmon-core.ps1 -Sanitize
.\tools\validate-kmon-live.ps1 -ObserveSeconds 300 -ImageStressFixtures -RequireImageCompletion -ProbeDriver -RequireQueueHealth -RequireCompletedWork
.\tools\validate-kmon-live.ps1 -ObserveSeconds 240 -ImageSweepFixtures -RequireImageCompletion -ProbeDriver -RequireQueueHealth -RequireCompletedWork
```

각 실제 실행은 새로운 증거 디렉터리를 사용한다. `validation.json`, 원시 JSONL,
캡처 파일, 대조 프로그램 출력과 종료 상태를 보관한다. `report.py`와 `compare.py`는
원시 결과를 독립적으로 집계하고 실행 파일의 PE 섹션에서 기대 페이지 수도 계산한다.
ASan은 핵심 엔진에 적용했으며 전체 KMON 실행 파일의 ASan 검증이라는 뜻은 아니다.
Release 빌드와 전체 자체 검사 종료 코드는 0이었다. 자체 검사 결과는 timeline 28,
MCP 89, console 557, commands 2,961, remote 66 및 연결 옵션 4개 통과다.
핵심 엔진 ASan 검사는 7개 그룹, hunting 11,326, pages 54, FP 49개를 통과했다.
기존 KernelMonitor.cpp의 C4244 경고는 남아 있으며 빌드 실패는 없었다.

Release 전체 자체 검사와 핵심 엔진 ASan 검사에는 허용된 두 목적지, 미등록·범위 밖
목적지, 불안정한 두 번째 읽기, 비실행 목적지, 잘린 표, 중복 fixup, 잘못된 BDD와
외부 thunk 형태를 포함한다. 공유 BDD를 반복 참조하는 표의 노드 처리 예산과
도달 불가 목적지 제외도 검사한다. 96페이지 전체 변조 시 64페이지에서 중단하고 나머지
32페이지로 재개하며, 정상 96페이지는 같은 상한 안에서 모두 처리한다. 묶음 중
원본 쓰기 시도가 공유 위반으로 거부되는지도 검사한다. 배경 대형 첫 순회와 감시
대상·일반 배경 작업의 배정 비율도 회귀 검사에 포함한다.
원시 이벤트 3,000건으로 분석 큐를 채운 뒤에도 원본 커서가 유지되고 종료 시
3,000건 모두 분석되는지 검사한다. 원본 용량을 1,024건으로 줄인 대조에서는
남은 1,024건을 처리하고 밀려난 1,976건을 손실로 보고한다. 종료 경계 바로 앞의
한 건만 사라진 경우도 손실 집계에 포함된다.

구조체와 REL32 의미는 Microsoft의
[Windows SDK winnt.h](https://github.com/microsoft/win32metadata/blob/main/generation/WinSDK/RecompiledIdlHeaders/um/winnt.h),
PE 실행 섹션과 재배치의 기준은 [PE 형식](https://learn.microsoft.com/en-us/windows/win32/debug/pe-format)을 사용했다.
호스트의 실제 DVRT와 원본/실행 중 분기 값은 `inspect-dvrt.py`, `dvrt.log`로 대조했다.
