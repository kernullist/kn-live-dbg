# KMON 전체 프로세스 레이아웃 큐 검증 (2026-10-23)

기준 커밋은 `6a93807`이다. 이전 [대형 이미지 검증](KMON_LARGE_IMAGE_VALIDATION_20261023.md)에
남았던 전체 프로세스 레이아웃 큐 포화를 실제 드라이버 실행으로 재현했다.
증거는 `.build/kmon-all-layout-20261023`에 보관했다.

## 원인과 수정

기존 수집기는 프로세스마다 최대 8개 후보를 전달하면서, 분석 큐가 거부해도
순회 커서를 전진시켰다. 200개 이상 프로세스의 반복 관측이 소비 속도를 넘으면
2,048개 큐가 찼고, 대기한 후보는 30초 유효기간을 넘겨 거절되기도 했다.
별도로 초기·최신·진행 중 스냅샷의 합계가 262,144개 영역 한도를 채워
새 순회가 실패했다. 기준 실행에는 `region_capacity` 상태 기록 2,348개가 남았다.

다음 변경을 적용했다.

- 레이아웃 후보 접수 한도를 128개로 두고, 거부된 변경 후보와 주기적 VA 커서를
  수집기에 보관한다. 수락한 경우에만 커서와 예산을 소비한다. 동일 인스턴스·매핑·
  역할의 대기 작업은 병합할 수 있지만 변경 후보를 주기적 후보로 덮어쓰지 않는다.
- 최대 8개 접수 예산, 이미 제출한 주소, 남은 순회 영역 수를 주기 전체에 유지한다.
  재시도가 새 예산을 만들거나 같은 스냅샷을 한 바퀴 넘어 중복 제출하지 않는다.
  변경 후보 최대 4개에는 실행 가능 영역을 우선하고, 남는 자리에 NX 전환도 보존한다.
- 보관 한도는 영역 524,288개, 이미지 이름 16,384개로 늘린다. 여전히 유한하며
  초과는 수집 실패로 표시한다. 분석 큐 저장소의 2,048개 한도를 늘려 밀린 작업을
  더 오래 보관하는 방식은 사용하지 않는다.
- 완료·실패 통지와 최대 16개 변화 이벤트를 진단 큐에 한 묶음으로 접수한다.
  512개 중 레이아웃 접수 한도는 384개이며, 공간이 없으면 원본 통지 하나를
  프로세스에 보관하고 다음 순회를 기다린다. 다른 생산자의 캡처 결과가 밀려나는
  현상도 함께 해결한다.
- 프로세스가 종료돼도 보관 중인 통지·변경 후보는 먼저 분석 경로에 넘긴다.
  종료 시 최대 10초 동안 유한한 원본 대기분을 배출한다. 진단 큐를 비운 직후에도
  접수를 재시도한다. 새 주기적 검사는 시작하지 않는다.
- 생성 시각·매핑·경로 재확인과 30초 만료 검사는 유지한다. 거절한 후보마다
  `coverage.layout_verification`에 이유를 남기며 검사 성공이나 탐지로 계산하지 않는다.

`layout_deferred`와 `layout_notices_deferred`는 재시도 횟수다. 실제 유실과 구분하며,
원본 대기·소실, 큐 대기·유실, 병합·접수 횟수를 따로 공개한다. 검증기는
`접수 = 재확인 성공 + 거절 + 병합 + 큐 대기`를 확인하고, 거절 기록 수 및 완료된
레이아웃 통지 수가 해당 처리 카운터와 일치하는지도 검사한다.

## 재현 조건과 검증

같은 부팅의 Windows 11 테스트 PC(2 CPU, 4 GiB, 테스트 서명)에서
각 실행을 순차 진행했다. 실행 중 빌드나 다른 KMON 세션을 겹치지 않았다.
전체 프로세스 모드는 PID·이름 필터 없이 시작한 뒤 대조군을 watch 목록에 추가한다.
종료 전·후 JSON으로 `scope=all_processes`, 완전한 프로세스 목록, 프로세스 한도 초과 0,
대조군보다 큰 실제 수집 범위를 확인한다.

```powershell
tools/build.ps1 -Configuration Release
x64/Release/KnLiveDbg.exe --self-test all
tools/validate-process-layout.ps1 -Sanitize
tools/validate-kmon-core.ps1 -Sanitize
tools/validate-kmon-live.ps1 -AllProcessLayouts -ImageSweepFixtures -ObserveSeconds 300 -ProbeDriver -RequireQueueHealth -RequireCompletedWork -RequireImageCompletion
```

실제 실행의 7개 시나리오는 `hold`, `mapped-readonly`, `overwrite`,
`orphan-mapped-rx`, `orphan-private`, `orphan-image`, `overwrite-tail`이다.
정상 2개는 예상하지 않은 finding/implant/hollow 이벤트가 없어야 하며,
양성 5개는 각 조건의 탐지가 있어야 한다. 레이아웃 변화 관측을 악성 판정으로
취급하지 않는 기존 규칙 외에 새 예외나 프로세스 이름 화이트리스트를 추가하지 않았다.
각 시나리오의 EXE·KERNEL32·KernelBase·ntdll, 합계 28개 고정 이미지의 순회를
확인하며 읽기 실패가 있거나 알려진 이미지가 검사되지 않았으면 실패한다.
기존 동적 재배치 제외 바이트는 완료된 순회와 별도로 남긴다.

자체 검사에는 큐 거절 후 같은 커서 재시도, 재시도 간 예산·중복 방지,
NX 전환 보존, 종료된 프로세스의 원본 후보 보존, 통지 묶음 접수,
진단 큐만 찬 종료 경계가 포함된다. Release 전체 검사와 레이아웃 ASan
105,078회 검사(실패 0), KMON core ASan 7개 그룹·hunting 11,326·pages 54·FP 49가
통과했다. 실행 로그는 `build-g.log`, `selftest-g.log`, `layout-asan-e.log`,
`core-asan-b.log`에 남겼다.

## 오탐 확인과 남는 범위

`full-b`와 `final-b`에서 배경 PID 12472의 `node.exe`와 `skia.node`가 현재 경로의
파일과 다른 PE 식별자로 관측됐다. 저장된 DOS/NT 헤더를 독립적으로 비교하면
node는 timestamp·entry RVA·image size·checksum 네 필드가 다르고,
skia는 checksum이 달랐다. 실제 차이를 기록한 것이며 원인이나 악성 여부를
확정하지 않는다. `event_category=observation`, `maliciousness=not_established`를
유지했다. 근거는 각 실행의 `identity-audit.json`과 해당 metadata capture다.
`final-c`에서는 대조군 밖의 코드 변경·레이아웃 이미지 식별자 finding이 없었다.

최종 거절 184건은 만료 175건과 프로세스·매핑 변경/접근 불가 9건,
561건은 만료 538건과 재확인 불가 23건이었다. 각 건의 이유를 저장했으며 검사
성공으로 집계하지 않았다. 두 실행의 종료 스냅샷에는 접근 불가 프로세스 13개씩과
이미지 이름 수집 실패가 있는 스냅샷 191/183개가 남았다. 이름 실패 집계는
질의 실패와 저장 한도 초과를 합친 영역 단위 값으로 고유 이미지 수가 아니다.
`final-c`에는 주소 공간/순회 만료 상태 기록 33개도 있었다. 이 범위는 미검증으로 남긴다.
캡처의 실제 읽기 실패는 두 실행 모두 12,288바이트, 알려진 읽기 불가 구간은
344,064/81,920바이트였고 순회·결과·파일 장부에서 제외하지 않았다.

큐 손실 0은 모든 프로세스의 모든 바이트를 검사했다는 뜻이 아니다. 접근 불가,
프로세스 종료·매핑 변경, 오래된 후보, 폴링 사이의 짧은 상태, 최초 관측 이전 변경은
계속 별도 한계다. 소스의 주기적 순회 커서가 남거나 대형 이미지의 전체 비교가
완료되지 않을 수 있다. 캡처 요청의 순회·바이트 장부가 맞더라도 명시된 읽기 실패나
제외 구간이 정상 바이트로 바뀌는 것은 아니다. 각 실패는 coverage에 남긴다.

2026-10-23에 재확인한 [Microsoft VirtualQueryEx 문서](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-virtualqueryex)는
COW 이후에도 `MEM_IMAGE`/`MEM_MAPPED`가 유지될 수 있음을 명시한다.
[ReadProcessMemory 문서](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-readprocessmemory)는
읽는 범위 전체에 대한 접근 가능성을 요구한다. 따라서 레이아웃 재확인·바이트 비교·
읽기 실패를 별도로 보고하는 원칙을 유지했다.
